# Блок E — подготовка переезда на сервер: отчёт

Пошаговая инструкция: **[DEPLOY_RUNBOOK.md](DEPLOY_RUNBOOK.md)**.

## 1. Что уже есть на сервере и что изменилось

**Что стоит на сервере** (по `DEPLOY.md` и папке `deploy/`; сам сервер я не смотрел):

- nginx с HTTPS, один сертификат Let's Encrypt на три адреса: `vitalo.uz` (Mini App), `admin.vitalo.uz`, `api.vitalo.uz`;
- PostgreSQL 16 на том же сервере, база `vitalo`, вход без пароля через локальный сокет;
- службы `vitalo-api` и `vitalo-bot` (бот сам опрашивает Telegram);
- ночной бэкап `vitalo-backup.timer` (03:30, хранение 14 дней);
- брандмауэр ufw (22/80/443), fail2ban, вход по SSH только по ключу;
- код обновляется командой `git push server main` и скриптом `update.sh`.

**Что изменилось с тех пор.** По моим данным, последний раз на сервер отправлялся коммит `2016a61` (версия MVP,
миграции до `20261004300000`). С тех пор локально сделано около 30 коммитов и 9 миграций:

| Что появилось | Нужна ли новая служба на сервере |
| --- | --- |
| Справочники, закупки, банки (Physical ID), приёмка, «Сверка» | нет |
| Заказы Яндекса и синхронизация (опрос раз в 5 минут) | нет — работает внутри `vitalo-api` |
| Приём уведомлений Яндекса (вебхук) | нет — адрес на `api.vitalo.uz`, выключен до фазы 6 |
| Банки в заказах Mini App | нет |
| Расходы, налог, зарплаты, аналитика; напоминания 12-го и 14-го | нет — внутри `vitalo-api` |
| Печать этикеток | нет — страница админки, печатает с вашего компьютера |
| Сообщение «Новые адреса VITALO» и туннель | на сервере **не работают и не нужны**: адреса постоянные |

**Службы, которые должны работать на сервере:** `nginx`, `postgresql`, `vitalo-api`, `vitalo-bot`,
`vitalo-backup.timer`, `certbot.timer`, `fail2ban`, `ufw`. Новых служб нет. Файлы nginx и systemd не менялись —
заново копировать их не нужно.

**Важная находка.** На сервере стоит **старый** `update.sh`: он не знает `--check` и применяет миграции сам, без
вопроса. Команда `update.sh --check` на нём запустила бы полное обновление. Поэтому в инструкции (фазы 0 и 2) первый
запуск делается **новым** скриптом, который сначала достаётся в отдельную папку. Проверка версии — одна команда,
она в инструкции.

| Скрипт | Что делает |
| --- | --- |
| `preflight.sh` | проверка сервера: версии, диск, брандмауэр (только 22/80/443), Postgres/Redis/API не видны снаружи, SSH по ключу, fail2ban, службы, сертификат, права `.env`. Только читает; секреты не печатает |

| `restore-check.sh` | восстанавливает копию во временную базу, сравнивает с рабочей, удаляет временную |
| `healthcheck.sh` | API жив, база жива, синхронизация Яндекса не старше N минут, место на диске, службы, возраст копии |
| `transfer-restore.sh` | перенос, шаг 1: копия с компьютера → новая база `vitalo_new` рядом с рабочей, таблица чисел для сверки |
| `transfer-swap.sh` | перенос, шаг 2: базы меняются местами; старая не удаляется, печатается способ вернуть назад |

**Скрипт для компьютера:** `scripts/export-dev-db.ps1` — копия `vitalo_dev` для сервера. Базу только читает; проверяет,
что всё остановлено и миграции применены. **Я его не запускал** — запускаете вы на шаге 3.2.

**В коде**

- **`GET /api/health`** — открытый адрес для мониторинга, без секретов: `200`, если всё хорошо; `503`, если база не
  отвечает или включённый опрос Яндекса молчит дольше 20 минут. Подходит для UptimeRobot одним адресом
  `https://api.vitalo.uz/api/health`.
- **`npm run server:after-transfer`** — запускается один раз сразу после переноса базы (проверка по умолчанию;
  запись — только с `--confirm --database=vitalo`; действие пишется в журнал аудита). Он:
  - переводит неотправленные сообщения в «пропущено», чтобы боевой бот не разослал сообщения с домашнего компьютера;
  - сбрасывает все входы (все войдут заново);
  - блокирует четырёх демо-сотрудников;
  - печатает список для сверки и «что проверить до открытия».

  Заказы, банки, остатки и историю он **не трогает**.

## 3. Тестовые заказы: почему остаются помеченными, а не удаляются

Вы просили скрипт очистки только если это возможно без нарушения целостности банок и истории. **Безопасно удалить
тестовые заказы нельзя**, поэтому скрипта удаления я не делал:

- у тестовых заказов есть банки, а в истории каждой банки записано «зарезервирована под заказ №…», «передана в
  доставку», «возврат» — после удаления заказа эти записи указывали бы в пустоту;
- движения склада и журнал аудита тоже ссылаются на заказы — остаток перестал бы объясняться движениями;
- связи в базе не дадут удалить заказ, пока на него ссылаются банки и история, — пришлось бы удалять и их, то есть
  стирать часть настоящей истории склада.

Пометка «ТЕСТ» (Этап 3) даёт тот же результат без риска: такие заказы не входят в аналитику, налог и сводки и
скрываются галочкой «Скрыть тестовые». Тестовые покупатели остаются (на них ссылаются тестовые заказы),
демо-сотрудники блокируются.

- Сборка сервера — без ошибок. Админка, Mini App и бот в этом блоке не менялись.
- `/api/health` и `healthcheck.sh` проверены вживую на тестовой базе: `200` и «всё в порядке»; при недоступном API —
  «ПЛОХО» и код ошибки.
- Локальная работа не затронута: `start.bat`, `stop.bat`, туннель и скрипты бота не менялись.

**Чего я проверить не мог.** Серверные скрипты (`preflight.sh`, `backup.sh`, `restore-check.sh`, `transfer-*.sh`)
проверены только на синтаксис: запускать их негде, кроме сервера. Они написаны так, чтобы при любой ошибке
останавливаться, ничего не удаляя. Первый запуск каждого — под вашим наблюдением, по инструкции; если вывод не похож
на описанный, остановитесь и пришлите его.

## 5. Что делать вам и в каком порядке

Сначала на компьютере:

1. Применить миграцию Этапа 3 к `vitalo_dev` (по [отчёту Этапа 3](operations/STAGE_3_REPORT.md)), проверить магазин.
2. Пометить тестовые заказы (`npm run orders:mark-test`, тот же отчёт).

Затем по [DEPLOY_RUNBOOK.md](DEPLOY_RUNBOOK.md):

| Фаза | Что | Где |
| --- | --- | --- |
| 0 | отправить код, проверить сервер (`preflight.sh`) | компьютер + сервер |
| 1 | резервная копия серверной базы и `.env`, копию базы — к себе | сервер + компьютер |
| 2 | обновить код и базу (`update.sh --check`, затем `--migrate`) | сервер |
| 3 | перенести данные: копия `vitalo_dev` → сервер, сверка, замена, `server:after-transfer` | компьютер + сервер |
| 4 | дописать `.env`: новые секреты, ключи Яндекса; пробный режим Яндекса | сервер |
| 5 | проверить nginx и HTTPS | сервер |
| 6 | вебхук Яндекса | сервер + кабинет Яндекса |
| 7 | бэкапы: проверить восстановление, скачать копию | сервер + компьютер |
| 8 | боевой бот, BotFather (`https://vitalo.uz`) | Telegram |
| 9 | тестовый заказ от начала до конца | магазин и админка |
| 10 | на компьютере выключить опрос Яндекса | компьютер |
| 11 | чек-лист перед открытием, мониторинг | — |

Фазы 0–3 лучше пройти за один раз (1,5–2 часа), когда вы не торгуете: между копией базы на компьютере и запуском
сервера в учёте ничего менять нельзя.

## 6. Открытые вопросы (я не угадывал — выбрал безопасный вариант)

1. **Есть ли на сервере настоящие заказы и покупатели?** Перенос заменяет серверную базу копией с компьютера.
   Безопасный выбор: старая база не удаляется, а шаг 3.4 показывает, сколько на сервере заказов и покупателей, — если
   там есть настоящие, инструкция велит остановиться. Тогда нужен другой план (перенос только каталога и банок).
2. **Что именно стоит на сервере.** Я исходил из того, что последний раз отправлялся коммит `2016a61`. Если вы
   обновляли сервер позже, список миграций в фазе 2 будет короче — это нормально, инструкция это учитывает.
3. **Реквизиты карты и настройки.** Переедут те, что в `vitalo_dev`. Если настоящие реквизиты вы вписывали только в
   серверной админке — впишите их заново (чек-лист, фаза 11; `server:after-transfer` напомнит, если стоят тестовые).
4. **Есть ли вы среди сотрудников в `vitalo_dev` со своим настоящим Telegram ID?** Если вы всегда входили локально
   «без Telegram», вашей записи там может не быть. Шаг 3.6 показывает список и даёт команду добавить себя.
5. **Настоящие заказы Яндекса в `vitalo_dev`.** Если локальная синхронизация работала в рабочем режиме, они есть и
   за ними закреплены банки. Они переедут как есть — **не помечайте их тестовыми**.
6. **Где в кабинете Яндекса регистрируется адрес уведомлений.** Точное место в интерфейсе я проверить не могу; в
   фазе 6 описан ожидаемый путь. Пока вебхук не зарегистрирован, заказы приходят опросом — ничего не теряется.
7. **Redis.** В коде сервера он не используется, в `DEPLOY.md` не ставится. `preflight.sh` проверит: если он всё же
   установлен, то не должен быть виден снаружи.
8. **Копия `.env` в бэкапе.** Теперь ночной бэкап кладёт копию `.env` в закрытую папку на сервере. На компьютер её
   скачивать не предлагаю (секреты). Если хотите вообще не хранить копию — скажите, уберу.
9. **`503` у `/api/health` при молчащем Яндексе.** Мониторинг пришлёт тревогу, хотя магазин работает. Я счёл это
   полезным (иначе пропуск заказов Яндекса никто не заметит). Если будет мешать — можно оставить `503` только для базы.
