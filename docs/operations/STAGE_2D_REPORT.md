# Этап 2D — заказы Яндекса приходят сами (только чтение)

Дата: 10.10.2026. Решения: [DECISIONS.md](DECISIONS.md), S2D-1…S2D-11 (с дополнением владельца «Д» — «Закрыть как
неактуальный»). Коммиты: `efa0bf3` (API), `bdd3349` (админка), этот отчёт — отдельным коммитом.

По умолчанию всё выключено: опрос не идёт (`YANDEX_SYNC_ENABLED=false`), режим DRY_RUN, вебхук выключен.
В Яндекс ничего не пишется ни в каком режиме.

## Что сверено с документацией Яндекса

- Список заказов — `POST v1/businesses/{businessId}/orders` (getBusinessOrders); метод кампании
  `GET v2/campaigns/{id}/orders` устарел и отключается 12.04.2027. Фильтры: кампании, дата обновления,
  номера заказов, `fake=false`; страницы по `pageToken`, до 50 заказов.
- Авторизация — заголовок `Api-Key: <токен>`; токен не истекает, нужен доступ на чтение заказов.
- Цены позиции (`payment`, `cashback`, `subsidy`) — **суммы за все единицы**; цена за штуку для нас =
  (payment + cashback + subsidy) / количество.
- Лимиты: 10 000 запросов в час, до 6 параллельных; превышение — HTTP 420 (заголовки
  `X-RateLimit-Resource-*`). Ошибки — `{status: "ERROR", errors: [{code, message}]}`.
- Уведомления API: `PING`, `ORDER_CREATED`, `ORDER_STATUS_UPDATED`, `ORDER_CANCELLED`, `ORDER_UPDATED` (только номер
  заказа и кампания); ответ 200 с `version`, `name`, `time` (PING — за 1 секунду, остальные — 10 секунд); при
  ошибке Яндекс повторяет и задерживает следующие. Подписи нет — только HTTPS и сети отправителя.

Источники: [getBusinessOrders](https://yandex.ru/dev/market/partner-api/doc/ru/reference/orders/getBusinessOrders),
[getOrders (устарел)](https://yandex.ru/dev/market/partner-api/doc/ru/reference/orders/getOrders),
[API-уведомления](https://yandex.ru/dev/market/partner-api/doc/ru/push-notifications/),
[POST notification](https://yandex.ru/dev/market/partner-api/doc/ru/push-notifications/reference/sendNotification),

[OpenAPI Яндекса](https://github.com/yandex-market/yandex-market-partner-api).

## Что сделано

**API**
- `src/marketplace/yandex/yandex-client.ts` — клиент: таймаут 15 с, 3 повтора с паузой (2, 10, 30 с) на сеть,
  таймаут, 5xx и 420 (параллельный лимит); исчерпанный лимит (420, Remaining 0) — без повторов, понятная ошибка;
  остаток лимита запоминается и виден на экране; токен вырезается из любых текстов.
- `src/marketplace/yandex/yandex-order.ts` — проверка формы ответа по каждому заказу, цена за штуку, таблица статусов.
- `src/marketplace/yandex/yandex-sync.ts` — опрос по расписанию, «Проверить сейчас», DRY_RUN, обработка заказа
  (своя транзакция + advisory-lock на номер), «Требует внимания», закрытие, уведомления в Telegram.
- `src/marketplace/yandex/yandex-sync.controller.ts` — экран синхронизации (только админ) и вебхук (выключен).
- `src/marketplace/yandex-orders.ts` — создание и отмена заказа вынесены в функции транзакции (их вызывает и
  синхронизация, «от имени системы»), кнопка «Зарезервировать банки», статус Яндекса в карточке.
- Уведомления: шаблоны `staff.yandex_new_order`, `staff.yandex_attention`, `staff.yandex_late_summary`; отправка
  по ролям (`toStaffRoles`) — только сотрудникам.
- `deploy/api.env.example` — имена переменных (без значений токена).

**Админка**
- «Синхронизация Яндекса» (только админ): режим, опрос, «токен задан / не задан», кабинет и кампании, лимит,
  последний запуск, «Проверить сейчас», журнал запусков с подробностями (в DRY_RUN — «что было бы сделано» и
  ответы Яндекса), «Требует внимания» с ответом Яндекса и «Закрыть как неактуальный».
- Карточка заказа Яндекса: «Статус Яндекса», номер и кампания, «создан синхронизацией»; «Не хватает остатка» с
  кнопкой «Зарезервировать банки».

Права: `yandex.sync` — только админ (экран, «Проверить сейчас», закрытие, сырые ответы). Заказы Яндекса и их
карточки — как в 2C (склад и админ работают, менеджер смотрит без денег).

## Миграция и как применить к vitalo_dev (делает владелец)

`apps/api/prisma/migrations/20261011100000_stage2d_yandex_sync/migration.sql` — только добавляет: 6 колонок с
умолчаниями в `marketplace_orders` (источник, «не хватает остатка», статус Яндекса), таблицы
`marketplace_external_orders` (увиденные заказы Яндекса, сырой ответ, «Требует внимания») и `yandex_sync_runs`
(журнал запусков), индексы, CHECK и запрет удаления. Существующие строки не меняются. Если миграция 2C ещё не
применена — сначала она (команда `migrate deploy` применит обе по порядку).

PowerShell, из корня проекта:

```powershell
docker compose exec -T postgres pg_dump -U vitalo -d vitalo_dev --format=custom --file /tmp/vitalo_dev-before-2d.dump
docker compose cp postgres:/tmp/vitalo_dev-before-2d.dump backups\vitalo_dev-before-2d.dump
docker compose exec -T postgres rm -f /tmp/vitalo_dev-before-2d.dump
cd apps\api
npx prisma migrate status
npx prisma migrate deploy
npx prisma generate
cd ..\..
```

Откат: остановить API, затем
`docker compose cp backups\vitalo_dev-before-2d.dump postgres:/tmp/vitalo_dev-before-2d.dump` и
`docker compose exec -T postgres pg_restore -U vitalo -d vitalo_dev --clean --if-exists /tmp/vitalo_dev-before-2d.dump`.

| `YANDEX_BUSINESS_ID` | `216755072` | кабинет |

| `YANDEX_SYNC_DAYS` | `3` | окно опроса (по дате обновления) |

## Сценарий проверки на dev

1. Примените миграцию (выше). В `apps/api/.env` добавьте `YANDEX_API_KEY=<токен>` и `YANDEX_SYNC_ENABLED=true`
   (`YANDEX_SYNC_DRY_RUN` не трогайте — по умолчанию DRY_RUN). `stop.bat`, `start.bat`.
2. Админка → **Синхронизация Яндекса**: «Режим: DRY_RUN», «Токен: задан», кабинет 216755072 / 149165806.
3. Нажмите **«Проверить сейчас»** (или подождите ~30 секунд после старта: первый автоматический запуск).
   Ошибка «не принял токен» или «нет доступа» — проверьте токен и его доступ на чтение заказов.
4. Откройте запуск в **журнале**: каждый заказ за 14 дней и что было бы сделано («создал бы заказ», «создал бы
   без банок», «в Требует внимания», «пропущен — ждём»). Кнопка «Ответы Яндекса» — сырые ответы.
   В «Заказах Яндекса» ничего не появилось, сообщений в Telegram нет.
5. Если в журнале всё ожидаемо, включите рабочий режим: `YANDEX_SYNC_DRY_RUN=false`, перезапустите API.
6. «Проверить сейчас»: заказы в статусе «В обработке» появятся в **Заказах Яндекса** со статусом «Новый» и
   зарезервированными банками; вам и складу придёт «🟡 Новый заказ Яндекса № …». Заказов нет — в журнале
   «Найдено: 0», это нормально.
7. Старые отгруженные и отменённые заказы окажутся в **«Требует внимания»** (одно сводное сообщение) — закройте их
   кнопкой «Закрыть…» с причиной «Старый заказ, уже обработан вручную».
8. Откройте созданный заказ: «Статус Яндекса» совпадает с кабинетом Яндекса. Дальше — сборка по 2C.

## Как включить уведомления Яндекса после переезда на сервер

1. На сервере в `.env` API: `YANDEX_WEBHOOK_SECRET=<16+ случайных символов>`, `YANDEX_WEBHOOK_ENABLED=true`;
   перезапустить API. Опрос оставить включённым — он страховка.
2. Настоящий адрес отправителя nginx уже передаёт (`proxy_set_header X-Real-IP $remote_addr;` в
   `deploy/nginx/snippets/vitalo-api-proxy.conf`). Проверить только, что API не доступен снаружи мимо nginx
   (`HOST=127.0.0.1` в `.env` API) — иначе `X-Real-IP` можно подделать.
3. Кабинет Яндекса → Настройки → API и модули → API-уведомления → «Подключить уведомления» → магазин VITALO_h →
   типы: создание заказа, изменение статуса, отмена, изменение заказа → адрес
   `https://admin.vitalo.uz/api/yandex/notifications/<YANDEX_WEBHOOK_SECRET>`.
4. Яндекс пришлёт PING: в кабинете подключение должно стать активным. Новый заказ появится в «Журнале запусков»
   как запуск «уведомление». Журнал уведомлений — в кабинете, «API и модули → Журнал уведомлений».

## Риски и как закрыты

| Риск | Как закрыт |
| --- | --- |
| Потеря уведомления | Уведомление — только ускорение; опрос раз в 5 минут перечитывает заказы, изменённые за 3 дня. Уведомление во время опроса не отбрасывается, а ждёт в очереди |
| Повтор уведомления, повторный опрос | Номер заказа уникален (маркетплейс + номер) в заказах и в увиденных заказах; обработка под advisory-lock на номер; сообщения — один раз (отметки времени отправки) |
| Дубли заказов | То же; заказ, введённый вручную с тем же номером, связывается, а не создаётся заново |
| Утечка токена | Токен только в `.env`; в журнал, ошибки, техчат и ответы не попадает (вырезается, даже если Яндекс его повторит); экран показывает только «задан»; тесты используют поддельный ключ и проверяют все места хранения |
| Превышение лимитов | ~12 запросов в час при опросе раз в 5 минут; повторы с паузой; исчерпанный лимит — без повторов, ошибка запуска с датой сброса; запуски не пересекаются |
| Ошибка посреди пакета | Каждый заказ — своя транзакция; ошибка считается и пишется в журнал и в карточку увиденного заказа, остальные обрабатываются; битая форма ответа — «Требует внимания» |
| Авто-резерв при нехватке | Всё или ничего в savepoint: при нехватке заказ создаётся без банок, «Не хватает остатка», резерв только кнопкой |
| Статусы Яндекса вне таблицы | Не создаём и не меняем ничего: «Требует внимания» с сырым ответом; у созданного заказа — только показ |
| Персональные данные в сыром ответе | Ответ Яндекса может содержать адрес доставки: хранится как есть, виден только админу (экран синхронизации) |

## Открытые вопросы

1. **Токен и его доступ.** Нужен Api-Key кабинета с доступом `inventory-and-order-processing:read-only` (или
   `all-methods:read-only`). Добавьте его в `apps/api/.env` как `YANDEX_API_KEY` — значение мне не присылайте.
2. **Окно первого запуска** — 14 дней по дате обновления. Заказы в «В обработке» за это время будут созданы и
   зарезервированы. Если какие-то из них уже собраны и отправлены вручную вне системы — после первого рабочего
   запуска их нужно отменить в карточке (или закрыть в «Требует внимания», если они там).
3. **Адрес доставки** в сырых ответах Яндекса (если он там есть) хранится в базе. Если хотите, могу вырезать
   из сохраняемого JSON поля `delivery.address` и `buyer`.
