Решения владельца по вопросам Q1–Q15 из аудита ([docs/OPERATIONS_AUDIT.md](../OPERATIONS_AUDIT.md), раздел 16).
Утверждено: 06.10.2026. Новые или изменённые решения дописываются сюда с датой. Старые не удаляются, а помечаются «заменено».

## Решения Этапа 2A — закупки (08.10.2026)

| № | Решение |
| --- | --- |
| S2A-1 | Ozon-аккаунты и поставщики — **справочники** (Настройки → Справочники, только Admin). Названия правятся в админке; значения не удаляются, только архивируются. Стартовые значения: Ozon-аккаунты «Сиадкомол», «Хадича», «Сиирожиддин», «Мастура», «Ислом»; поставщик «Glorious Health Nutrition». |
| S2A-2 | Все суммы — целые **UZS**. «Итоговая фактическая сумма» = сколько реально заплатили за закупку; доставка отдельно не считается (если она была, она уже внутри итоговой суммы). |
| S2A-3 | Статусов закупки два: **EXPECTED** (ожидается) и **RECEIVED** (получено). «Отменена полностью» не статус, а вычисляется: по всем строкам отменено = заказано. RECEIVED ставится сам, когда по всем строкам ничего не ожидается и хоть что-то получено. |
| S2A-4 | Округление себестоимости: база строки = (заказано − отменено) × цена; разница с итоговой суммой распределяется пропорционально базам **методом наибольших остатков** (при равных остатках — более ранняя строка), сумма строк совпадает с итоговой точно. Себестоимость единицы = floor(сумма строки / количество), оставшиеся сумы по 1 — на первые единицы. |
| S2A-5 | Отмена Ozon — **событие** (журнал закупки неизменяем), закупка никогда не удаляется. Отменить можно не больше «заказано − отменено − получено»; повтор того же запроса не удваивает отмену. |

### Решения для Этапа 2B (приёмка и Physical ID), зафиксированы заранее

- Срок годности хранится **датой**, вводится и показывается в формате **ДД.ММ.ГГГГ**.
- Этикетка **75×120 мм**, принтер XPrinter XP-365B (ширина печати 76 мм, 203 DPI).
- На этикетке — **короткий состав RU/UZ**: отдельные поля товара, заполняет Admin (не полный состав из карточки).
- Начальный остаток переводится в единицы (PhysicalUnit) **после инвентаризации**; себестоимость единиц начального остатка = текущий `cost_uzs` товара.
- Сканера пока нет: Physical ID вводится вручную; USB-сканер позже работает как клавиатура (тот же ввод).

## Решения Этапа 2B — Physical ID, приёмка, этикетки (09.10.2026)

| № | Решение |
| --- | --- |
| S2B-1 | Срок годности единицы — **дата**, вводится и показывается как **ДД.ММ.ГГГГ**, **обязателен**. Прошедший срок не принимается; меньше 90 дней — только после подтверждения «Всё равно принять?». |
| S2B-2 | Этикетка **75×120 мм** (XP-365B, 203 DPI, печать из браузера, поля 2 мм): Physical ID крупно, штрихкод Code 128 с Physical ID, SKU, «Состав:» (короткий RU), «Tarkibi:» (короткий UZ), «Срок годности / Yaroqlilik muddati:». **Без названия товара и без номеров заказов.** Короткий состав заполняют Admin и Manager; если пусто — предупреждение, печать разрешена. Каждая печать — событие LABEL_PRINTED, повторная печать разрешена. |
| S2B-3 | Начальные остатки — по **листу пользователя** «Начальные остатки (банки)» (`npm run import:opening-stock`, по умолчанию проверка без записи). Лист — истина. Себестоимость единиц = `products.cost_uzs` (пусто — ошибка). При «Завершить» остаток **приводится корректировкой** (adjustment «Начальный остаток по пересчёту, лист пользователя»); если резерв заказов больше числа единиц — завершение запрещено. Товар переходит на учёт по единицам только при завершении. |
| S2B-4 | Старые операции с количеством (приход, списание, корректировка, возврат на склад; и колонка остатка в импорте товаров) для товаров с учётом по единицам **заблокированы**: «Товар учитывается по единицам: используйте «Приёмка»». Admin может провести операцию только с явным флагом обхода и **обязательной причиной**; это пишется в журнал аудита, расхождение покажет «Сверка». |
| S2B-5 | Номера Physical ID — из последовательности Postgres `physical_unit_seq`: формат V-000184. **Пропуски номеров допустимы** (откат транзакции, отменённая приёмка), **повторное использование запрещено**: единицы не удаляются (отмена → статус «Отменена»), номер единицы не меняется. |
| S2B-6 | **ВРЕМЕННОЕ ПРАВИЛО до Этапа 2C: не принимать реальные заказы на товары с учётом по единицам.** Заказы уменьшают остаток (`inventory.actual_qty`), но не единицы: единицы со склада не списываются, «Сверка» показывает это как ожидаемое расхождение. |
| S2B-7 | Сканера нет: Physical ID вводится вручную (V-000184, v-000184, 000184 и 184 — одно и то же). USB-сканер позже работает как клавиатура в том же поле (+ Enter); при русской раскладке «V» приходит как «М» — это тоже понимается. |
| S2B-8 | **Заменяет S2B-2 (08.10.2026, по решению пользователя).** Этикетка Physical ID — **58×40 мм** (размер — настройка «Настройки → Печать», по умолчанию 58×40; @page по размеру, поля 2 мм): Physical ID крупно моноширинным, SKU, «Годен до / Yaroqli:» ДД.ММ.ГГГГ и **QR-код только с Physical ID** (строится в браузере, без внешних запросов). Не печатаются: название, короткий состав, номера заказов, цена, себестоимость. Короткий состав больше не проверяется и не предупреждает (поля товара остаются). Макет 75×120 оставлен в коде как неиспользуемый шаблон (для будущей этикетки на курьерский пакет). Страница печати открывается в обычном Chrome по **билету печати**: выдаёт вошедший сотрудник, только для этой приёмки/единицы, 15 минут, перестаёт действовать при выходе/блокировке; токен сотрудника в ссылку не попадает. |

Как это устроено:

- Приёмка по закупке: источник (Ozon-аккаунт или поставщик) → ожидаемые позиции (остаток по всем закупкам EXPECTED источника) → «Принять»: количество и сроки годности → Physical ID в статусе «Принята» → этикетки → «Завершить»: в одной транзакции единицы «На складе», `received_qty` закупок, статус закупки, остаток (+приход со ссылкой на приёмку). Повторное «Завершить» ничего не удваивает.
- Принятое делится по закупкам источника от старых к новым (внутри закупки — по порядку строк). Сверх ожидаемого — после подтверждения, как расхождение на последней строке (событие закупки DISCREPANCY).
- Себестоимость единицы: k-я единица строки получает k-ю долю распределённой суммы строки (S2A-4), сумма по строке совпадает с распределённой; единицы сверх ожидаемого — среднюю стоимость строки. При изменении итоговой суммы или отмене Ozon себестоимость единиц строки пересчитывается (событие COST_CHANGED).
- Manager и Склад не получают с сервера себестоимость единиц, закупочные цены, суммы и номера заказов Ozon (в том числе в событиях); Admin видит всё.

## Решения Этапа 2C — заказы Яндекса и жизненный цикл банок (10.10.2026)

| № | Решение |
| --- | --- |
| S2C-1 | **Заказ Яндекса — отдельная сущность** (`marketplace_orders`, маркетплейс `yandex`), уникальность (маркетплейс, номер заказа). Позиции — товар, количество, цена продажи за единицу; банки — через таблицу назначений «строка ↔ банка» (Q3, Q5). Заказы, позиции и назначения не удаляются (триггер). Статусы: **Новый → Собран → Передан в доставку → Доставлен**; **Отменён** (только до передачи) и **Возврат** (после передачи или доставки). Переходы проверяются в сервисе и триггером в базе; каждый пишется в журнал аудита с автором и временем. |
| S2C-2 | **Резерв банки сразу при вводе заказа** (принято владельцем): при создании система резервирует конкретные банки по **FEFO** (ранний срок годности, затем меньший номер). Всё или ничего; строки банок блокируются (`FOR UPDATE SKIP LOCKED`), строка остатка — условным UPDATE; повтор запроса с тем же Idempotency-Key ничего не удваивает. Одна банка — не больше одного активного заказа (частичный уникальный индекс). |
| S2C-3 | **Мягкий FEFO с причиной** (принято владельцем): при сборке каждая банка подтверждается вводом Physical ID. Банка того же товара может заменить зарезервированную; если есть банка с более ранним сроком — предупреждение «рекомендуем V-…», продолжить можно только с причиной (пишется в историю банки, назначение и журнал аудита). |
| S2C-4 | **Остаток и резервы.** На полке (в `inventory.actual_qty`) — банки «На складе» и «Зарезервирована». Резерв банки под Яндекс — +1 к `reserved_qty`, рядом с резервами VITALO по количеству (до 2E). Поэтому «доступно» = остаток − резерв для Mini App и админки сразу учитывает Яндекс; банку резервируют, только если свободна хотя бы одна единица (VITALO-резервы тоже считаются). **Списание с остатка — при «Передан в доставку»** (банка физически ушла); «Доставлен» — банки «Продана». Отмена до передачи — резерв снимается. |
| S2C-5 | **Возврат на проверку** (принято владельцем): отмена после передачи или возврат после доставки → заказ «Возврат», банки «Возврат на проверке» (в остатке их нет). Решение склада по каждой банке: «Вернуть на склад» (срок и целостность проверены, причина; просроченную нельзя) → «На складе», остаток +1; или «Списать» (причина) → «Списана». |
| S2C-6 | **Прибыль заказа Яндекса** (принято владельцем): **цена − комиссия (цена × %) − себестоимость конкретных банок**; логистика Яндекса не считается. Комиссия хранится в заказе (по умолчанию — см. S2C-11); комиссию и цены после создания правит только Admin. Себестоимость, комиссию и прибыль видит только Admin (сервер их другим ролям не отдаёт). |
| S2C-7 | **Роли** (принято владельцем): Склад — заказы Яндекса (создание, сборка, передача, доставлен, отмена и возврат), решение по возврату, «Потеряна» и «Найдена». Admin — всё это плюс списание, корректировка, комиссия и цены. ~~Manager — без доступа~~ **уточнено 10.10.2026 (S2C-13):** Manager **видит список и карточку** заказов Яндекса без себестоимости, комиссии и прибыли, действий нет. Marketer — без доступа. Просмотр «Единиц» у Manager — как в 2B. |
| S2C-8 | **Статусы банки и переходы** (триггер в базе = таблица в коде): На складе ↔ Зарезервирована → В доставке (Яндекс) → Продана (Яндекс); В доставке / Продана → Возврат на проверке → На складе или Списана; На складе ↔ Потеряна; Списана — из «На складе», «Возврат на проверке», «Потеряна» (только Admin, причина: истёк срок / повреждена / прочее). Корректировка (только Admin, причина обязательна): срок годности; статус между «На складе», «Потеряна», «Списана» и из «Возврат на проверке» в «Потеряна». Банку заказа корректировкой не двигают. Физическое удаление запрещено. |
| S2C-9 | **«Сверка»**: банки на полке (На складе + Зарезервирована) против остатка. Заказы Яндекса двигают банки и остаток вместе. Расхождение ровно на проданное заказами VITALO после начального остатка помечается **«только заказы VITALO (до 2E)»** и ошибкой не считается. |
| S2C-10 | **S2B-6 остаётся в силе до 2E:** реальные заказы VITALO на товары с учётом по банкам не принимать. Заказ VITALO уменьшает остаток, но не банки, поэтому банку, физически ушедшую по заказу VITALO, нельзя отмечать «Потеряна» (остаток уменьшится второй раз). |
| S2C-11 | **Комиссия по умолчанию из карточки товара** (решение владельца 10.10.2026): `yandex_commission_percent` товара, если заполнена, иначе **18.5 %**. В заказе один процент: если товаров несколько и проценты разные — средний, взвешенный по выручке строк (2 знака). Admin может задать комиссию при создании и изменить потом. |
| S2C-12 | **Цена продажи подставляется из карточки товара** (решение владельца 10.10.2026): цена Яндекса (`yandex_price_uzs`) появляется в форме «Новый заказ», при создании её можно изменить (Admin и Склад). Если в карточке цены нет и её не ввели — ошибка «укажите цену». После создания цену меняет только Admin. Для формы склад получает только цену Яндекса нужных товаров (`GET /staff/yandex-orders/price-hints`). |
| S2C-13 | **Manager: просмотр заказов Яндекса** (решение владельца 10.10.2026): право `yandex.orders.view` (Manager, Склад, Admin) — список и карточка; сервер не отдаёт Manager себестоимость, комиссию и прибыль. Создание, сборка, передача, доставка, отмена, правки — `yandex.orders` (Склад, Admin): у Manager 403, в админке кнопок нет. |
| S2C-14 | **Остаток уменьшается при «Передан в доставку»** — подтверждено владельцем 10.10.2026, без изменений (S2C-4). |

## Решения Этапа 2D — заказы Яндекса приходят сами (10.10.2026)

| № | Решение |
| --- | --- |
| S2D-1 | **Опрос — основной путь, уведомления — страховка ускорения.** Опрос по расписанию (по умолчанию каждые 5 минут) читает заказы кампаний, изменённые за последние N дней (3; при первом запуске режима — 14). Уведомление Яндекса содержит только номер заказа: заказ всё равно читается из API и обрабатывается той же функцией, что и опрос. Потерянное уведомление подберёт следующий опрос. |
| S2D-2 | **Метод Яндекса — `POST v1/businesses/{businessId}/orders`** (метод кампании `GET v2/campaigns/{id}/orders` устарел, отключается 12.04.2027). Business ID 216755072 и список кампаний (149165806, VITALO_h) — настройки. **Цена за штуку = (payment + cashback + subsidy) / количество** (Яндекс даёт суммы за все единицы), округление до сума; принимаются только цены в UZS, иначе — «Требует внимания». Тестовые заказы Яндекса (`fake`) не берутся. |
| S2D-3 | **Только чтение.** В 2D нет ни одного запроса, меняющего данные в Яндексе (статусы, цены, остатки). Токену достаточно доступа `inventory-and-order-processing:read-only` (или `all-methods:read-only`). |
| S2D-4 | **Включение — переменными.** `YANDEX_SYNC_ENABLED=false` (по умолчанию опрос выключен; «Проверить сейчас» работает всегда); **`YANDEX_SYNC_DRY_RUN=true` по умолчанию**: ничего не создаётся, в журнал запусков пишется «что было бы сделано» и ответы Яндекса. Рабочий режим включает владелец после проверки. |
| S2D-5 | **Авто-резерв как при ручном вводе (2C):** заказ из `PROCESSING` создаётся «Новый», позиции по offerId = SKU, комиссия по правилам 2C (из карточки, иначе 18.5 %), банки по FEFO, всё или ничего. **Не хватает остатка → заказ создаётся без банок с пометкой «Не хватает остатка»** (без резерва) + «Требует внимания»; кнопка «Зарезервировать банки» (склад, админ) делает резерв позже, тоже всё или ничего. |
| S2D-6 | **Таблица статусов Яндекса.** `PLACING`, `RESERVED`, `UNPAID`, `PENDING` — не подтверждён, ждём. `PROCESSING` — создаём. Впервые увиден в `DELIVERY`, `PICKUP`, `DELIVERED`, `CANCELLED`, `RETURNED`, `PARTIALLY_RETURNED` — не создаём (банки могли уже уйти), «Требует внимания», одно сводное сообщение на запуск. Для созданного заказа: `CANCELLED` до передачи — наша отмена (банки на склад), после передачи — «Возврат» и банки «на проверку» (2C); `RETURNED` / `PARTIALLY_RETURNED` — «Требует внимания», наш статус не меняется (какие банки вернулись — решает человек); остальные статусы только показываются как «Статус Яндекса». Неизвестный статус — «Требует внимания». |
| S2D-7 | **«Требует внимания»** (админ): неизвестный SKU, товар без учёта по банкам, не UZS, битый ответ, не хватает остатка, впервые увиден поздно, возврат в Яндексе, неизвестный статус — с причиной и сырым ответом Яндекса. **«Закрыть как неактуальный»** (решение владельца, пункт Д): только админ, причина обязательна, в журнал аудита; закрытый заказ больше не поднимается опросами и не даёт уведомлений (если он связан с нашим заказом, статус Яндекса по нему продолжает обновляться, отмена в Яндексе по-прежнему отменяет). |
| S2D-8 | **Уведомления API отложены до сервера:** эндпоинт `POST /api/yandex/notifications/<секрет>` есть, но выключен (`YANDEX_WEBHOOK_ENABLED=false`, иначе 404) и в Яндексе не зарегистрирован. Подписи у уведомлений Яндекса нет, поэтому защита — секрет в адресе (16+ символов) и адрес отправителя из сетей Яндекса (5.45.207.0/25, 141.8.142.0/25, 5.255.253.0/25; за nginx — `X-Real-IP`). Ответ сразу (PING — за 1 с), обработка после ответа. |
| S2D-9 | **Telegram:** новый заказ — склад и админ (номер Яндекса, товары и количество, кнопка «Открыть в админке»); проблема — админ. Сообщения ставятся в ту же очередь `notifications` в той же транзакции, что и изменение; повторный опрос и повторное уведомление не дают дублей. Клиентам ничего не отправляется. |
| S2D-10 | **Токен** — только в `apps/api/.env` (`YANDEX_API_KEY`), не в коде, тестах, журнале и отчётах. Экран показывает лишь «задан / не задан»; из любых текстов ошибок токен и секрет вебхука вырезаются. |
| S2D-12 | **Персональные данные покупателя не сохраняются** (решение владельца 10.10.2026). Ответ Яндекса проходит белый список ДО записи в базу и журнал: остаются только номер заказа, кампания, статусы, даты, признаки (fake, cancelRequested, тип оплаты) и позиции (offerId, название, количество, суммы и валюта). Поля buyer, delivery (адрес, получатель, телефоны), notes и любые новые поля отбрасываются. В Telegram и журнал аудита они тоже не попадают. |
| S2D-11 | **Надёжность пакета:** каждый заказ Яндекса обрабатывается в своей транзакции под advisory-lock на номер; ошибка одного заказа считается и записывается, остальные обрабатываются. Дубли невозможны: номер заказа уникален в паре (маркетплейс, номер) и в таблице заказов, и в таблице увиденных заказов. |
