# VITALO Operations — утверждённые решения

Решения владельца по вопросам Q1–Q15 из аудита ([docs/OPERATIONS_AUDIT.md](../OPERATIONS_AUDIT.md), раздел 16).
Утверждено: 06.10.2026. Новые или изменённые решения дописываются сюда с датой. Старые не удаляются, а помечаются «заменено».

| № | Вопрос | Решение | Статус |
| --- | --- | --- | --- |
| Q1 | Что значит остаток по товару (`inventory.actual_qty`) при поштучном учёте | При переходе на PhysicalUnit **остаток по товару становится производным от PhysicalUnit** (вариант c). | Утверждено, будет сделано при переходе |
| Q2 | Как Mini App узнает о единицах, ушедших в Yandex | **Переходный период:** назначение единицы в заказ Yandex уменьшает «доступно» для Mini App. **Затем** «доступно» считается из PhysicalUnit. | Утверждено |
| Q3 | Где хранить заказы Yandex | **Отдельная сущность** заказа Yandex с **общим интерфейсом** заказа. Текущая таблица `orders` под Yandex **не расширяется**. | Утверждено |
| Q4 | Категории товара | Остаются **многие-ко-многим и два дерева** («потребность», «тип продукта»). В Operations показывается **основная категория**. | Утверждено |
| Q5 | Строка заказа с `qty > 1` | **Отдельная таблица назначений «строка заказа ↔ физическая единица».** | Утверждено |
| Q6 | Начальные единицы под текущий остаток | Единицы создаются **после инвентаризации со сроками годности**. | Утверждено |
| Q7 | Деньги пришли после автоотмены заказа | **Восстановить заказ, если товар есть в наличии**, иначе — возврат денег клиенту. | Утверждено, не реализовано |
| Q8 | «Я оплатил(а)» долго не проверяют | **Напоминание менеджерам через N часов.** | **Сделано в Этапе 0** (настройка `payment_check_reminder_hours`, шаблон `staff.payment_check_overdue`) |
| Q9 | Права на деньги | **Себестоимость видит только Admin** (`costs.view`). **Marketer — без выручки** (`dashboard.revenue` только у admin и manager). **Manager получит складские права вместе с поштучным складом.** | Себестоимость и выручка — **сделано в Этапе 0**; права manager на склад — при переходе |
| Q10 | Миграции на production | **Только вручную**: `update.sh` без флага не применяет миграции, только с `--migrate` или после ответа `yes`. | **Сделано в Этапе 0** |
| Q11 | Локальная база и защита seed | Локальная рабочая база — **`vitalo_dev`**, на сервере остаётся `vitalo`. **Seed защищён по имени базы** (только `*_dev` / `*_test`). | Защита — **сделано в Этапе 0**; переименование — `scripts/rename-local-db.ps1` (запускает владелец) |
| Q12 | Задачи склада | **Отдельная таблица задач** (не расширять `manager_tasks`). | Утверждено |
| Q13 | Уведомления операций | **Общая Telegram-группа операций** плюс **личные сообщения admin и manager на переходный период**. | Утверждено |
| Q14 | Источник заказов Yandex | Заказы приходят **через API Яндекс Маркета**: уведомления на адрес сервера плюс опрос для сверки. **Telegram-парсер не нужен.** | Утверждено |
| Q15 | SKU товаров, которые продаются на Яндексе | **Внутренний SKU заменяется на SKU Яндекса.** Старые заказы хранят свой снимок (`order_items.sku_snapshot`) и не меняются. | **Уточнено 07.10.2026:** SKU Яндекса равен нашему (TPRD-…), замена не требуется. Импорт только предупреждает, если они различаются |

## Решения Этапа 1 (07.10.2026)

| № | Решение |
| --- | --- |
| S1-1 | SKU на Яндексе равен нашему TPRD-…: замены SKU по Q15 не требуется. Если в таблице они различаются — только предупреждение, ничего не переименовывается. |
| S1-2 | В модель товара входит **платёжный сбор Яндекса** (`yandex_payment_fee_percent`, «поручение на перевод платежа») наряду с комиссией (`yandex_commission_percent`) и фиксированной логистикой за заказ (`yandex_logistics_uzs`). Эти три поля видит и меняет только Admin (`costs.view`). |
| S1-3 | TPRD-026 объединён с TPRD-024 (лист «Объединено» в таблице Яндекса импорт не читает). |
| S1-4 | Новые товары из таблицы Яндекса создаются со статусом **hidden**: видны только в админке, в Mini App не показываются, пока их не заполнят и не включат. |
| S1-5 | **Цена VITALO (`price_uzs`) применяется в Mini App сразу** после сохранения — без вопросов. Импорт таблицы Яндекса цену VITALO не меняет, только показывает расхождение. |
| S1-6 | Окно «Вы уже изменили цену в Яндекс Маркете?» — **только про цену Яндекса**. Ответ «Нет» ставит отметку «требует синхронизации»; снять её могут Admin и Manager. |
| S1-7 | Справочники (бренды, производители, страны, формы) — отдельные таблицы. Текстовые поля товара остаются и питают Mini App; при выборе и переименовании значения они обновляются автоматически. Значения не удаляются, только архивируются. |

## Что из этого уже влияет на код

- **Этап 0 (выполнен):** Q8, Q9 (себестоимость и выручка), Q10, Q11 (защита и подготовка переименования).
- **Этап 1 (выполнен):** справочники, поля Яндекса, скрипты `backfill:dictionaries` и `import:yandex` (S1-1…S1-7).
- **Остальное** — входные условия для следующих этапов. Перед каждым этапом проверить, что решение не поменялось.

## Что следует из решений для архитектуры (без реализации)

- Q1 + Q2: на переходный период остаётся текущий количественный учёт (`inventory`) как источник «доступно» для Mini App. Любое назначение единицы Yandex обязано уменьшать «доступно». После перехода «доступно» = свободные PhysicalUnit.
- Q3 + Q14: канал Yandex — отдельная сущность заказа и адаптер API Яндекс Маркета. Источником истины остаётся внутренняя запись, а не входящие уведомления.
- Q5: `order_items.qty` сохраняется; связь с единицами — через отдельную таблицу назначений.
- Q15: смена SKU у товара не трогает `order_items.sku_snapshot` в уже созданных заказах.
