# VITALO Operations — утверждённые решения

Решения владельца по вопросам Q1–Q15 из аудита ([docs/OPERATIONS_AUDIT.md](../OPERATIONS_AUDIT.md), раздел 16).
Утверждено: 06.10.2026. Новые или изменённые решения дописываются сюда с датой. Старые не удаляются, а помечаются «заменено».

## Решения Этапа 2A — закупки (08.10.2026)

| № | Решение |
| --- | --- |
| S2A-1 | Ozon-аккаунты и поставщики — **справочники** (Настройки → Справочники, только Admin). Названия правятся в админке; значения не удаляются, только архивируются. Стартовые значения: Ozon-аккаунты «Сиадкомол», «Хадича», «Сиирожиддин», «Мастура», «Ислом»; поставщик «Glorious Health Nutrition». |
| S2A-2 | Все суммы — целые **UZS**. «Итоговая фактическая сумма» = сколько реально заплатили за закупку; доставка отдельно не считается (если она была, она уже внутри итоговой суммы). |
| S2A-3 | Статусов закупки два: **EXPECTED** (ожидается) и **RECEIVED** (получено). «Отменена полностью» не статус, а вычисляется: по всем строкам отменено = заказано. RECEIVED ставится сам, когда по всем строкам ничего не ожидается и хоть что-то получено. |
| S2A-4 | Округление себестоимости: база строки = (заказано − отменено) × цена; разница с итоговой суммой распределяется пропорционально базам **методом наибольших остатков** (при равных остатках — более ранняя строка), сумма строк совпадает с итоговой точно. Себестоимость единицы = floor(сумма строки / количество), оставшиеся сумы по 1 — на первые единицы. |
| S2A-5 | Отмена Ozon — **событие** (журнал закупки неизменяем), закупка никогда не удаляется. Отменить можно не больше «заказано − отменено − получено»; повтор того же запроса не удваивает отмену. |

### Решения для Этапа 2B (приёмка и Physical ID), зафиксированы заранее

- Срок годности хранится **датой**, вводится и показывается в формате **ДД.ММ.ГГГГ**.
- Этикетка **75×120 мм**, принтер XPrinter XP-365B (ширина печати 76 мм, 203 DPI).
- На этикетке — **короткий состав RU/UZ**: отдельные поля товара, заполняет Admin (не полный состав из карточки).
- Начальный остаток переводится в единицы (PhysicalUnit) **после инвентаризации**; себестоимость единиц начального остатка = текущий `cost_uzs` товара.
- Сканера пока нет: Physical ID вводится вручную; USB-сканер позже работает как клавиатура (тот же ввод).

## Решения Этапа 2B — Physical ID, приёмка, этикетки (09.10.2026)

| № | Решение |
| --- | --- |
| S2B-1 | Срок годности единицы — **дата**, вводится и показывается как **ДД.ММ.ГГГГ**, **обязателен**. Прошедший срок не принимается; меньше 90 дней — только после подтверждения «Всё равно принять?». |
| S2B-2 | Этикетка **75×120 мм** (XP-365B, 203 DPI, печать из браузера, поля 2 мм): Physical ID крупно, штрихкод Code 128 с Physical ID, SKU, «Состав:» (короткий RU), «Tarkibi:» (короткий UZ), «Срок годности / Yaroqlilik muddati:». **Без названия товара и без номеров заказов.** Короткий состав заполняют Admin и Manager; если пусто — предупреждение, печать разрешена. Каждая печать — событие LABEL_PRINTED, повторная печать разрешена. |
| S2B-3 | Начальные остатки — по **листу пользователя** «Начальные остатки (банки)» (`npm run import:opening-stock`, по умолчанию проверка без записи). Лист — истина. Себестоимость единиц = `products.cost_uzs` (пусто — ошибка). При «Завершить» остаток **приводится корректировкой** (adjustment «Начальный остаток по пересчёту, лист пользователя»); если резерв заказов больше числа единиц — завершение запрещено. Товар переходит на учёт по единицам только при завершении. |
| S2B-4 | Старые операции с количеством (приход, списание, корректировка, возврат на склад; и колонка остатка в импорте товаров) для товаров с учётом по единицам **заблокированы**: «Товар учитывается по единицам: используйте «Приёмка»». Admin может провести операцию только с явным флагом обхода и **обязательной причиной**; это пишется в журнал аудита, расхождение покажет «Сверка». |
| S2B-5 | Номера Physical ID — из последовательности Postgres `physical_unit_seq`: формат V-000184. **Пропуски номеров допустимы** (откат транзакции, отменённая приёмка), **повторное использование запрещено**: единицы не удаляются (отмена → статус «Отменена»), номер единицы не меняется. |
| S2B-6 | **ВРЕМЕННОЕ ПРАВИЛО до Этапа 2C: не принимать реальные заказы на товары с учётом по единицам.** Заказы уменьшают остаток (`inventory.actual_qty`), но не единицы: единицы со склада не списываются, «Сверка» показывает это как ожидаемое расхождение. **Снято этапом 2E (S2E-12).** |
| S2B-7 | Сканера нет: Physical ID вводится вручную (V-000184, v-000184, 000184 и 184 — одно и то же). USB-сканер позже работает как клавиатура в том же поле (+ Enter); при русской раскладке «V» приходит как «М» — это тоже понимается. |
| S2B-8 | **Заменяет S2B-2 (08.10.2026, по решению пользователя).** Этикетка Physical ID — **58×40 мм** (размер — настройка «Настройки → Печать», по умолчанию 58×40; @page по размеру, поля 2 мм): Physical ID крупно моноширинным, SKU, «Годен до / Yaroqli:» ДД.ММ.ГГГГ и **QR-код только с Physical ID** (строится в браузере, без внешних запросов). Не печатаются: название, короткий состав, номера заказов, цена, себестоимость. Короткий состав больше не проверяется и не предупреждает (поля товара остаются). Макет 75×120 оставлен в коде как неиспользуемый шаблон (для будущей этикетки на курьерский пакет). Страница печати открывается в обычном Chrome по **билету печати**: выдаёт вошедший сотрудник, только для этой приёмки/единицы, 15 минут, перестаёт действовать при выходе/блокировке; токен сотрудника в ссылку не попадает. |
| S2B-9 | **Перепечатка этикеток существующих банок пачкой.** В «Склад → Единицы» — галочки у строк, «выбрать все на странице» и «Напечатать этикетки выбранных»: до 50 этикеток за раз тем же билетом печати, что и одна этикетка (сервер не менялся, миграции нет). Печатаются только существующие банки: новые не создаются, Physical ID, статусы, сроки, себестоимость и остатки не меняются; в историю каждой банки пишется «Напечатана этикетка», счётчик «Этикеток» растёт на 1. Отменённую банку выбрать нельзя; если она всё же попала в печать — не печатается ничего. Выбор сбрасывается при смене страницы или фильтра. Роли — как у печати одной этикетки: Admin, Manager, Склад. |

Как это устроено:

- Приёмка по закупке: источник (Ozon-аккаунт или поставщик) → ожидаемые позиции (остаток по всем закупкам EXPECTED источника) → «Принять»: количество и сроки годности → Physical ID в статусе «Принята» → этикетки → «Завершить»: в одной транзакции единицы «На складе», `received_qty` закупок, статус закупки, остаток (+приход со ссылкой на приёмку). Повторное «Завершить» ничего не удваивает.
- Принятое делится по закупкам источника от старых к новым (внутри закупки — по порядку строк). Сверх ожидаемого — после подтверждения, как расхождение на последней строке (событие закупки DISCREPANCY).
- Себестоимость единицы: k-я единица строки получает k-ю долю распределённой суммы строки (S2A-4), сумма по строке совпадает с распределённой; единицы сверх ожидаемого — среднюю стоимость строки. При изменении итоговой суммы или отмене Ozon себестоимость единиц строки пересчитывается (событие COST_CHANGED).
- Manager и Склад не получают с сервера себестоимость единиц, закупочные цены, суммы и номера заказов Ozon (в том числе в событиях); Admin видит всё.

## Решения Этапа 2C — заказы Яндекса и жизненный цикл банок (10.10.2026)

| № | Решение |
| --- | --- |
| S2C-1 | **Заказ Яндекса — отдельная сущность** (`marketplace_orders`, маркетплейс `yandex`), уникальность (маркетплейс, номер заказа). Позиции — товар, количество, цена продажи за единицу; банки — через таблицу назначений «строка ↔ банка» (Q3, Q5). Заказы, позиции и назначения не удаляются (триггер). Статусы: **Новый → Собран → Передан в доставку → Доставлен**; **Отменён** (только до передачи) и **Возврат** (после передачи или доставки). Переходы проверяются в сервисе и триггером в базе; каждый пишется в журнал аудита с автором и временем. |
| S2C-2 | **Резерв банки сразу при вводе заказа** (принято владельцем): при создании система резервирует конкретные банки по **FEFO** (ранний срок годности, затем меньший номер). Всё или ничего; строки банок блокируются (`FOR UPDATE SKIP LOCKED`), строка остатка — условным UPDATE; повтор запроса с тем же Idempotency-Key ничего не удваивает. Одна банка — не больше одного активного заказа (частичный уникальный индекс). |
| S2C-3 | **Мягкий FEFO с причиной** (принято владельцем): при сборке каждая банка подтверждается вводом Physical ID. Банка того же товара может заменить зарезервированную; если есть банка с более ранним сроком — предупреждение «рекомендуем V-…», продолжить можно только с причиной (пишется в историю банки, назначение и журнал аудита). |
| S2C-4 | **Остаток и резервы.** На полке (в `inventory.actual_qty`) — банки «На складе» и «Зарезервирована». Резерв банки под Яндекс — +1 к `reserved_qty`, рядом с резервами VITALO по количеству (до 2E). Поэтому «доступно» = остаток − резерв для Mini App и админки сразу учитывает Яндекс; банку резервируют, только если свободна хотя бы одна единица (VITALO-резервы тоже считаются). **Списание с остатка — при «Передан в доставку»** (банка физически ушла); «Доставлен» — банки «Продана». Отмена до передачи — резерв снимается. |
| S2C-5 | **Возврат на проверку** (принято владельцем): отмена после передачи или возврат после доставки → заказ «Возврат», банки «Возврат на проверке» (в остатке их нет). Решение склада по каждой банке: «Вернуть на склад» (срок и целостность проверены, причина; просроченную нельзя) → «На складе», остаток +1; или «Списать» (причина) → «Списана». |
| S2C-6 | **Прибыль заказа Яндекса** (принято владельцем): **цена − комиссия (цена × %) − себестоимость конкретных банок**; логистика Яндекса не считается. Комиссия хранится в заказе (по умолчанию — см. S2C-11); комиссию и цены после создания правит только Admin. Себестоимость, комиссию и прибыль видит только Admin (сервер их другим ролям не отдаёт). |
| S2C-7 | **Роли** (принято владельцем): Склад — заказы Яндекса (создание, сборка, передача, доставлен, отмена и возврат), решение по возврату, «Потеряна» и «Найдена». Admin — всё это плюс списание, корректировка, комиссия и цены. ~~Manager — без доступа~~ **уточнено 10.10.2026 (S2C-13):** Manager **видит список и карточку** заказов Яндекса без себестоимости, комиссии и прибыли, действий нет. Marketer — без доступа. Просмотр «Единиц» у Manager — как в 2B. |
| S2C-8 | **Статусы банки и переходы** (триггер в базе = таблица в коде): На складе ↔ Зарезервирована → В доставке (Яндекс) → Продана (Яндекс); В доставке / Продана → Возврат на проверке → На складе или Списана; На складе ↔ Потеряна; Списана — из «На складе», «Возврат на проверке», «Потеряна» (только Admin, причина: истёк срок / повреждена / прочее). Корректировка (только Admin, причина обязательна): срок годности; статус между «На складе», «Потеряна», «Списана» и из «Возврат на проверке» в «Потеряна». Банку заказа корректировкой не двигают. Физическое удаление запрещено. |
| S2C-9 | **«Сверка»**: банки на полке (На складе + Зарезервирована) против остатка. Заказы Яндекса двигают банки и остаток вместе. Расхождение ровно на проданное заказами VITALO после начального остатка помечается **«только заказы VITALO (до 2E)»** и ошибкой не считается. |
| S2C-10 | **S2B-6 остаётся в силе до 2E:** реальные заказы VITALO на товары с учётом по банкам не принимать. Заказ VITALO уменьшает остаток, но не банки, поэтому банку, физически ушедшую по заказу VITALO, нельзя отмечать «Потеряна» (остаток уменьшится второй раз). **Снято этапом 2E (S2E-12).** |
| S2C-11 | **Комиссия по умолчанию из карточки товара** (решение владельца 10.10.2026): `yandex_commission_percent` товара, если заполнена, иначе **18.5 %**. В заказе один процент: если товаров несколько и проценты разные — средний, взвешенный по выручке строк (2 знака). Admin может задать комиссию при создании и изменить потом. |
| S2C-12 | **Цена продажи подставляется из карточки товара** (решение владельца 10.10.2026): цена Яндекса (`yandex_price_uzs`) появляется в форме «Новый заказ», при создании её можно изменить (Admin и Склад). Если в карточке цены нет и её не ввели — ошибка «укажите цену». После создания цену меняет только Admin. Для формы склад получает только цену Яндекса нужных товаров (`GET /staff/yandex-orders/price-hints`). |
| S2C-13 | **Manager: просмотр заказов Яндекса** (решение владельца 10.10.2026): право `yandex.orders.view` (Manager, Склад, Admin) — список и карточка; сервер не отдаёт Manager себестоимость, комиссию и прибыль. Создание, сборка, передача, доставка, отмена, правки — `yandex.orders` (Склад, Admin): у Manager 403, в админке кнопок нет. |
| S2C-14 | **Остаток уменьшается при «Передан в доставку»** — подтверждено владельцем 10.10.2026, без изменений (S2C-4). |

## Решения Этапа 2D — заказы Яндекса приходят сами (10.10.2026)

| № | Решение |
| --- | --- |
| S2D-1 | **Опрос — основной путь, уведомления — страховка ускорения.** Опрос по расписанию (по умолчанию каждые 5 минут) читает заказы кампаний, изменённые за последние N дней (3; при первом запуске режима — 14). Уведомление Яндекса содержит только номер заказа: заказ всё равно читается из API и обрабатывается той же функцией, что и опрос. Потерянное уведомление подберёт следующий опрос. |
| S2D-2 | **Метод Яндекса — `POST v1/businesses/{businessId}/orders`** (метод кампании `GET v2/campaigns/{id}/orders` устарел, отключается 12.04.2027). Business ID 216755072 и список кампаний (149165806, VITALO_h) — настройки. **Цена за штуку = (payment + cashback + subsidy) / количество** (Яндекс даёт суммы за все единицы), округление до сума; принимаются только цены в UZS, иначе — «Требует внимания». Тестовые заказы Яндекса (`fake`) не берутся. |
| S2D-3 | **Только чтение.** В 2D нет ни одного запроса, меняющего данные в Яндексе (статусы, цены, остатки). Токену достаточно доступа `inventory-and-order-processing:read-only` (или `all-methods:read-only`). |
| S2D-4 | **Включение — переменными.** `YANDEX_SYNC_ENABLED=false` (по умолчанию опрос выключен; «Проверить сейчас» работает всегда); **`YANDEX_SYNC_DRY_RUN=true` по умолчанию**: ничего не создаётся, в журнал запусков пишется «что было бы сделано» и ответы Яндекса. Рабочий режим включает владелец после проверки. |
| S2D-5 | **Авто-резерв как при ручном вводе (2C):** заказ из `PROCESSING` создаётся «Новый», позиции по offerId = SKU, комиссия по правилам 2C (из карточки, иначе 18.5 %), банки по FEFO, всё или ничего. **Не хватает остатка → заказ создаётся без банок с пометкой «Не хватает остатка»** (без резерва) + «Требует внимания»; кнопка «Зарезервировать банки» (склад, админ) делает резерв позже, тоже всё или ничего. |
| S2D-6 | **Таблица статусов Яндекса.** `PLACING`, `RESERVED`, `UNPAID`, `PENDING` — не подтверждён, ждём. `PROCESSING` — создаём. Впервые увиден в `DELIVERY`, `PICKUP`, `DELIVERED`, `CANCELLED`, `RETURNED`, `PARTIALLY_RETURNED` — не создаём (банки могли уже уйти), «Требует внимания», одно сводное сообщение на запуск. Для созданного заказа: `CANCELLED` до передачи — наша отмена (банки на склад), после передачи — «Возврат» и банки «на проверку» (2C); `RETURNED` / `PARTIALLY_RETURNED` — «Требует внимания», наш статус не меняется (какие банки вернулись — решает человек); остальные статусы только показываются как «Статус Яндекса». Неизвестный статус — «Требует внимания». |
| S2D-7 | **«Требует внимания»** (админ): неизвестный SKU, товар без учёта по банкам, не UZS, битый ответ, не хватает остатка, впервые увиден поздно, возврат в Яндексе, неизвестный статус — с причиной и сырым ответом Яндекса. **«Закрыть как неактуальный»** (решение владельца, пункт Д): только админ, причина обязательна, в журнал аудита; закрытый заказ больше не поднимается опросами и не даёт уведомлений (если он связан с нашим заказом, статус Яндекса по нему продолжает обновляться, отмена в Яндексе по-прежнему отменяет). |
| S2D-8 | **Уведомления API отложены до сервера:** эндпоинт `POST /api/yandex/notifications/<секрет>` есть, но выключен (`YANDEX_WEBHOOK_ENABLED=false`, иначе 404) и в Яндексе не зарегистрирован. Подписи у уведомлений Яндекса нет, поэтому защита — секрет в адресе (16+ символов) и адрес отправителя из сетей Яндекса (5.45.207.0/25, 141.8.142.0/25, 5.255.253.0/25; за nginx — `X-Real-IP`). Ответ сразу (PING — за 1 с), обработка после ответа. |
| S2D-9 | **Telegram:** новый заказ — склад и админ (номер Яндекса, товары и количество, кнопка «Открыть в админке»); проблема — админ. Сообщения ставятся в ту же очередь `notifications` в той же транзакции, что и изменение; повторный опрос и повторное уведомление не дают дублей. Клиентам ничего не отправляется. |
| S2D-10 | **Токен** — только в `apps/api/.env` (`YANDEX_API_KEY`), не в коде, тестах, журнале и отчётах. Экран показывает лишь «задан / не задан»; из любых текстов ошибок токен и секрет вебхука вырезаются. |
| S2D-12 | **Персональные данные покупателя не сохраняются** (решение владельца 10.10.2026). Ответ Яндекса проходит белый список ДО записи в базу и журнал: остаются только номер заказа, кампания, статусы, даты, признаки (fake, cancelRequested, тип оплаты) и позиции (offerId, название, количество, суммы и валюта). Поля buyer, delivery (адрес, получатель, телефоны), notes и любые новые поля отбрасываются. В Telegram и журнал аудита они тоже не попадают. |
| S2D-11 | **Надёжность пакета:** каждый заказ Яндекса обрабатывается в своей транзакции под advisory-lock на номер; ошибка одного заказа считается и записывается, остальные обрабатываются. Дубли невозможны: номер заказа уникален в паре (маркетплейс, номер) и в таблице заказов, и в таблице увиденных заказов. |
| S2D-13 | **Срок «Отгрузить до» у заказа Яндекса.** Берётся из `delivery.shipment` ответа Яндекса: `shipmentDate` (`ГГГГ-ММ-ДД`) и, если есть, `shipmentTime` (`ЧЧ:ММ` или `ЧЧ:ММ:СС`). Из блока `delivery` сохраняются только эти два значения — адрес покупателя и данные курьера по-прежнему вырезаются (S2D-12). Документация не обещает срок у каждого заказа, поэтому его отсутствие или непонятный формат — не ошибка: заказ создаётся как обычно, «срок не указан». Сообщение о новом заказе складу и администраторам: «Новый заказ Яндекс № …, отгрузить до ДД.ММ.ГГГГ [ЧЧ:ММ]»; без срока — прежний текст. По-прежнему одно сообщение на заказ (опрос и вебхук); срок, появившийся или изменившийся позже, обновляется в карточке без второго сообщения, а ответ без срока известный срок не стирает. В админке — колонка и строка «Отгрузить до» с пометками «сегодня» и «просрочено», пока заказ не передан в доставку. «Требует внимания» получают только администраторы. Миграция `20261016100000_yandex_ship_by`. |

## Решения Этапа 2E — банки (Physical ID) для заказов Mini App (13.10.2026)

| № | Решение |
| --- | --- |
| S2E-1 | **Только товары с учётом по банкам.** Позиции остальных товаров в заказе Mini App работают как раньше, по количеству (резерв при создании, списание при подтверждении оплаты). |
| S2E-2 | **Момент привязки — подтверждение оплаты** менеджером или админом («Подтвердить оплату», заказ становится `paid`, оплата `payment_success`). До оплаты действует обычный резерв по количеству на 12 часов. При оплате резерв количества **остаётся** (списания при оплате для таких товаров больше нет), а по FEFO закрепляются конкретные банки — всё или ничего; банки «Зарезервирована», в истории «Заказ VITALO №…». Повторное подтверждение ничего не дублирует. |
| S2E-3 | **Не хватает банок — оплата всё равно проходит.** Заказ оплачен, клиент получает обычное «оплачен», но заказ помечается **«Нужно внимание склада»** с причиной, админам и менеджерам уходит сообщение в Telegram. Количество остаётся в резерве заказа (никто другой его не купит). Собрать и отправить такой заказ нельзя, пока склад не нажмёт «Зарезервировать банки» (после приёмки, «Найдена», возврата). Обоснование: деньги клиента уже получены — терять оплату или показывать клиенту ошибку нельзя; расхождение «остаток больше, чем банок» — внутренняя проблема склада. |
| S2E-4 | **Сборка — как у Яндекса (S2C-3):** каждая банка подтверждается вводом Physical ID; другая свободная банка того же товара заменяет зарезервированную; не самый ранний срок — предупреждение и обязательная причина. Общий код FEFO для обоих каналов. |
| S2E-5 | **Одно списание — при «Передан в доставку»** (единое правило с Яндексом, S2C-4): банки «В доставке (VITALO)», остаток и резерв уменьшаются на количество банок, сохраняется **снимок себестоимости** каждой банки. «Доставлен» — банки «Продана (VITALO)». Старое списание при оплате для таких товаров отключено — двойного списания нет. |
| S2E-6 | **Отмена и возврат.** До оплаты — резерв количества снимается как раньше. После оплаты, до отправки — банки возвращаются «На складе», резерв количества снимается, задача на возврат денег. После отправки — **новое действие «Оформить возврат»** (раньше отмены после отправки в админке не было): заказ «Отменён» (был в доставке) или «Возврат» (был доставлен), банки «Возврат на проверке», решение по каждой — на складе по правилам 2C (S2C-5). |
| S2E-7 | **Одна банка — один заказ во всех каналах.** Банку нельзя закрепить за заказом Mini App и заказом Яндекса одновременно: это проверяют статус банки, уникальные индексы и триггеры в базе в обе стороны. |
| S2E-8 | **Права.** Новые действия с банками заказа Mini App («Сборка»: ввод Physical ID, «Зарезервировать банки», «Оформить возврат») — **Склад и Admin** (право `orders.units`). Manager видит блок «Сборка» без действий, без себестоимости и прибыли; Marketer заказы не видит. **Существующие права на заказы не менялись** (безопасный вариант): оплату подтверждает и заказ отменяет Manager/Admin, статусы «Сборка» и «Передан в доставку» двигают Manager и Склад, «В пути» и «Доставлен» — Manager. Замена банки, списание, корректировка — по правилам 2C. |
| S2E-9 | **Себестоимость и прибыль** (только Admin, `costs.view`): у каждой проданной банки хранится снимок её себестоимости на момент передачи в доставку; прибыль позиции = оплаченная цена − себестоимость этих банок, без доставки. |
| S2E-10 | **«Сверка».** Банок на полке (На складе + Зарезервирована) = остаток. Резерв = банки Яндекса + банки Mini App + резерв по количеству (неоплаченные заказы и оплаченные, ждущие банок). Пометка «только заказы VITALO (до 2E)» убрана. Осталась одна объяснимая разница — **«старые заказы без банок»**: заказы Mini App, оплаченные до 2E (списаны по количеству при оплате). |
| S2E-11 | **Старые заказы без банок** не трогаются и работают по-старому (система узнаёт их по тому, что заказ уже ничего не держит в резерве). Скрипт `npm run orders:attach-units` (проверка по умолчанию, `--confirm` — запись, только базы `_dev`/`_test`): оплаченным и ещё не отправленным закрепляет банки (количество возвращается на полку и в резерв заказа, дальше заказ идёт как обычный 2E); уже отправленные только перечисляет — какие банки физически ушли, система не знает, их отмечают вручную («Списать» или «Корректировка»). |
| S2E-12 | **S2B-6 и S2C-10 сняты:** заказы Mini App на товары с учётом по банкам можно принимать — банки и остаток теперь двигаются вместе. |
| S2E-13 | **Наклейка заказа Mini App, 75×120 мм.** Кнопка «Печать наклейки» в карточке заказа (блок «Отправка»); у заказов Яндекса её нет. Одна наклейка на заказ, чёрно-белая, без полей: «VITALO», дата, крупно номер заказа, «ПРЕДОПЛАЧЕНО», получатель и телефон, адрес, состав (артикул × количество, короткое название), QR-код с номером заказа; цен, себестоимости и номеров банок нет. Печатается только для оплаченного и не отменённого заказа. Печатают все, кто видит заказ: Admin, Склад, Manager. Необязательный «Номер накладной службы доставки» (BTS, Яндекс Go…) меняют Склад и Admin (право `orders.waybill`), он печатается на наклейке, если заполнен; покупателю не показывается. Персональные данные — только на странице печати и на бумаге: в журнал аудита пишется лишь факт «наклейка напечатана» с номером заказа. Страница печати открывается по билету на один заказ (15 минут, пока сотрудник в системе), как этикетки банок. Если позиций больше шести — первые пять и строка «…и ещё N поз.». Миграция `20261017100000_order_delivery_waybill` (одна колонка). |

## Решения Этапа 3 — расходы, налог, зарплаты, продажи и аналитика (14.10.2026)

| № | Решение |
| --- | --- |
| S3-1 | **Деньги видит и меняет только Admin.** Новое право `finance.manage` не выдано ни одной другой роли: «Аналитика», «Финансы» (расходы, налог, зарплаты), пометка «тест» и «Реальные расходы на доставку (наши)» в заказе. Сервер отказывает остальным ролям на каждом запросе, в меню этих разделов у них нет. Значок «ТЕСТ» (без сумм) видят все, кто видит заказ. Каждое изменение пишется в журнал аудита. |
| S3-2 | **Доставка, оплаченная клиентом в Mini App, — транзит:** не выручка и не расход, в оборот для налога не входит. Наши настоящие расходы на доставку — отдельное поле заказа (по умолчанию 0), его в любой момент меняет Admin. Порог бесплатной доставки уже был в коде (тариф, `free_shipping_threshold_uzs`; в Ташкенте бесплатно от 300 000 сум) — не менялся. |
| S3-3 | **Продажа признаётся в день, когда заказ стал «Доставлен»** (оба канала), по ташкентскому времени. Выручка VITALO — оплаченная цена товаров, выручка Яндекса — количество × цена продажи. |
| S3-4 | **Возврат считается в месяце, когда он оформлен:** отдельной записью с минусом он забирает выручку, комиссию и себестоимость банок. Месяц продажи не переписывается. Наши расходы на доставку возвратом не возвращаются. |
| S3-5 | **Тестовые заказы** (`is_test`) не входят никуда: аналитика, налог, сводки, дашборд. Снятие пометки возвращает заказ в расчёты. Скрипт `npm run orders:mark-test` (проверка по умолчанию, `--confirm` — запись, только базы `_dev`/`_test`) помечает заказы Яндекса с номером `TEST-…` и те номера, которые владелец сам перечислил в `--numbers=`; заказы VITALO он только показывает списком и ничего не угадывает. |
| S3-6 | **Налог с оборота.** Ставка хранится в настройках списком «с какого месяца» (сначала 1 %); менять можно только с текущего или будущего месяца, прошлые не пересчитываются. Оборот месяца = продажи месяца − возвраты месяца, без тестовых заказов. Налог считается по каждому каналу отдельно и складывается (поэтому каналы всегда сходятся с итогом), округляется до целого сума, не бывает отрицательным. Срок — до 14-го числа следующего месяца. «Отметить оплаченным» (дата и фактическая сумма) возможно только за закончившийся месяц; запись об оплате никогда не меняется — если расчёт позже изменился, показывается разница. |
| S3-7 | **Зарплаты.** Сотрудник (не обязательно пользователь системы): имя, сумма в месяц, месяц начала, активен. Новая сумма задаётся «с месяца» — только текущего или будущего и не раньше уже выплаченного. Начисления появляются сами с месяца начала. Зарплата за месяц выплачивается до 14-го числа следующего месяца (первая, за ноябрь 2026, — до 14.12.2026). Статусы: к выплате / выплачено / просрочено. Отключённому сотруднику текущий месяц ещё начисляется, следующие — нет. Имена вводит владелец, в базу заранее ничего не записано. |
| S3-8 | **Расходы.** Категории по умолчанию — «Упаковка», «Реклама», «Непредвиденные», «Прочее» (создаются при первом открытии раздела). Категорию с записями удалить нельзя — только скрыть. Расход удаляется с обязательной причиной и остаётся в базе и журнале. |
| S3-9 | **Чистая прибыль** = выручка − себестоимость − комиссия Яндекса − наши расходы на доставку − налог − прочие расходы − зарплаты. Все числа считает сервер одним способом. Прочие расходы и зарплаты по каналам не делятся: при выборе канала показывается прибыль канала до них, в режиме «Все каналы» они вычитаются один раз (строка «Общие»). Зарплаты за часть месяца берутся пропорционально дням. «Вложено в закупки» — только для сведения, в прибыль не входит (себестоимость уже учтена через проданные банки). |
| S3-10 | **Себестоимость — снимок стоимости именно проданных банок** на момент передачи в доставку. У заказов Яндекса такой снимок теперь тоже сохраняется (у старых берётся текущая стоимость банки). Если у позиции банок нет (товар без учёта по банкам, старые заказы до 2E) — себестоимость **неизвестна**: нулём не считается, выводится отдельной строкой, прибыль помечается «неполная». |
| S3-11 | **Напоминания в Telegram только админам:** 12-го — «14-го к оплате: налог X, зарплаты Y», 14-го — если что-то не отмечено оплаченным. Если компьютер в этот день был выключен, первое уйдёт 13-го, второе — до 20-го. Факт отправки хранится в базе: повторов после перезапуска нет. Если платить нечего, сообщение не отправляется. |
| S3-12 | **«Нужно внимание склада»** в списке заказов Mini App: счётчик над списком и фильтр. Считаются оплаченные заказы до передачи в доставку, которым не закреплены банки. Клиентская часть Mini App не менялась. |

## Решения Блока E — переезд на сервер (15.10.2026)

| № | Решение |
| --- | --- |
| S-E-1 | **Данные переносятся копией базы целиком** (`vitalo_dev` → сервер), а не повторным импортом: только так Physical ID, сроки, себестоимость и история банок совпадут с уже напечатанными этикетками. |
| S-E-2 | **Перенос в два шага с возможностью вернуться:** копия восстанавливается в новую базу `vitalo_new` рядом с рабочей, числа сверяются, затем базы меняются местами переименованием. Старая серверная база не удаляется (`vitalo_before_transfer_<дата>`), хранится минимум две недели после открытия. |
| S-E-3 | **Тестовые заказы не удаляются, а остаются с пометкой «ТЕСТ».** На них ссылаются история банок, движения склада и журнал аудита; удаление нарушило бы целостность учёта. Скрипта удаления нет намеренно. Тестовые покупатели остаются, демо-сотрудники блокируются. |
| S-E-4 | **Сразу после переноса, до запуска служб, выполняется `npm run server:after-transfer`** (проверка по умолчанию; запись — с `--confirm --database=<имя>`, имя должно совпасть с базой из настроек; аудит): неотправленные сообщения → «пропущено», все входы сбрасываются, демо-сотрудники блокируются. Заказы, банки, остатки и история не меняются. |
| S-E-5 | **Новых служб на сервере нет:** синхронизация Яндекса, вебхук, напоминания и фоновые задачи работают внутри `vitalo-api`; бот — long polling (вебхука у бота нет). Туннель Cloudflare на сервере не запускается: адреса заданы в настройках. |
| S-E-6 | **Mini App в проде — `https://vitalo.uz`** (nginx отдаёт собранные файлы и передаёт `/api` в API). Этот адрес указывается в BotFather. |
| S-E-7 | **`GET /api/health`** — открытый, без секретов и внутренних сведений: `200` — всё хорошо; `503` — база не отвечает или включённый опрос Яндекса не проходил дольше «3 интервала + 5 минут» (20 минут при опросе раз в 5). Для внешнего мониторинга одним адресом. |
| S-E-8 | **Яндекс на сервере включается ступенями:** опрос выключен → пробный режим (DRY_RUN) → рабочий режим — только после того, как на домашнем компьютере опрос выключен (два экземпляра не должны опрашивать одновременно). Вебхук — дополнение, опрос остаётся запасным. На сервере новый токен только для чтения, старый отзывается. |
| S-E-9 | **Секреты сервера создаются и вводятся только на сервере** (новый `BOT_API_SECRET`, `YANDEX_WEBHOOK_SECRET`, токены). В репозитории — только шаблон `apps/api/.env.production.example` с пустыми значениями. Ночной бэкап хранит копию `.env` в закрытой папке на сервере. |
| S-E-10 | **После запуска сервера учёт ведётся только там.** Локальная `vitalo_dev` становится учебной: приёмка и заказы в ней не ведутся, боевой токен бота на компьютер не ставится. |
| S-E-11 | **Копия базы восстанавливается от обычного пользователя `vitalo`, не от суперпользователя**, и любая ошибка `pg_restore` останавливает восстановление (неполная база удаляется). Для этого: `--no-owner --no-acl --no-comments` (владельцы, права и `COMMENT ON EXTENSION` из копии не переносятся); расширения `pg_trgm` и `unaccent` заранее создаёт сам `vitalo` (они «доверенные», владельцу базы это разрешено); восстановление идёт в три прохода (структура → данные → индексы и триггеры). Функция `vitalo_product_doc` вызывала `vitalo_norm` без имени схемы, из-за чего поисковый индекс товаров не восстанавливался ни из одной копии: исправлено миграцией `20261015100000_search_doc_schema_qualified` (данные не меняет), а для копий, сделанных до неё, то же исправление применяется между проходами. Восстановление из ночной копии и откат делаются тем же безопасным способом «новая база рядом → замена», а не `pg_restore --clean` поверх рабочей. |
| S-E-12 | **Уведомления Яндекса принимаются по двум путям:** `POST /api/yandex/notifications/<секрет>` и `POST /api/yandex/notifications/<секрет>/notification`. Яндекс вызывает `POST /notification` относительно адреса из кабинета (спецификация `sendNotification`), поэтому в кабинет вводится адрес без `/notification`. Логика одна: тот же секрет, та же проверка сетей Яндекса, та же обработка без дублей. Любой другой путь и неверный секрет — `404` (существование маршрута не раскрывается), верный секрет не с адреса Яндекса — `403`. Ответ по спецификации: `200` и `{version, name, time}` (строки 1–100 символов, время в UTC), на `PING` — до 1 секунды; ошибки — `{error: {type, message}}`. Из уведомления берётся только номер заказа, заказ запрашивается у Яндекса токеном уже после ответа; персональные данные не сохраняются (S2D-12). Секрет меняется одной командой (инструкция, шаг 6.6). Команды для `.env` в инструкции — без `sudo -i … bash -c` с переменными (они терялись из-за кавычек). |
