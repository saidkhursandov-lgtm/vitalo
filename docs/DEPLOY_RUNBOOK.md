# Переезд VITALO на сервер — пошаговая инструкция (Блок E)

Для кого: для владельца магазина, не программиста. Каждый шаг: **команда → что она делает → как понять, что всё хорошо**.

| Что | Значение |
| --- | --- |
| Сервер | Hostmaster VPS, Ubuntu 24.04, IP `91.213.99.230` |
| Магазин (Mini App) | https://vitalo.uz |
| Админка | https://admin.vitalo.uz |
| API | https://api.vitalo.uz |
| Боевой бот | @vitalo_uz_bot (свой токен, не тестовый) |
| Что переносим | код до Этапа 3 включительно и данные из `vitalo_dev`: каталог, банки с Physical ID, остатки, SKU-алиасы, настройки |

Первая установка сервера с нуля описана в [DEPLOY.md](../DEPLOY.md). Здесь — переезд на **уже настроенный** сервер.

## Правила на всё время переезда

1. **Секреты (токены, пароли) вводятся только на сервере** в редакторе `nano`. Не присылайте их в чат, не делайте
   скриншоты файла `.env`.
2. **Ничего не применяем без резервной копии.** Каждая фаза начинается с проверки, что копия есть.
3. **Идём по порядку.** После каждой фазы — раздел «Проверка». Если проверка не прошла, дальше не идём.
4. Если что-то непонятно или вывод не похож на описанный — **остановитесь** и пришлите вывод (без секретов).
5. Туннель Cloudflare на сервере **не запускается** — он нужен только на домашнем компьютере.

**Про `sudo`.** Команды, начинающиеся с `sudo`, при первом запуске спросят пароль вашего пользователя на сервере
(ввод не виден) — это нормально.

**Где вводить команды.** Блоки с пометкой `powershell` — на вашем компьютере в PowerShell. Блоки с пометкой `bash` —
на сервере. Вход на сервер с компьютера:

```powershell
ssh saidkomolkhursandov@91.213.99.230
```

Что делает: открывает окно сервера. Хорошо: строка начинается с `saidkomolkhursandov@vitalo:~$`. Пароль не
спрашивается (вход по ключу; может спросить фразу-пароль ключа).

## Фаза 0. Проверка сервера до начала

Ничего не меняет, только смотрит.

### 0.1 Отправить новый код на сервер (он пока не включается)

```powershell
cd C:\Users\PC_LENOVO\Documents\VITALO\vitalo
& "C:\Program Files\Git\cmd\git.exe" push server main
```

Что делает: кладёт новый код в хранилище на сервере. Магазин при этом **не меняется** — код включается только в
фазе 2. Хорошо: в конце строка вида `main -> main`.

### 0.2 Достать новый код в отдельную папку для проверок

Сейчас на сервере работает старая версия, в ней ещё нет новых скриптов. Возьмём их, не трогая работающий магазин:

```bash
sudo -iu vitalo bash -c 'cd /opt/vitalo/app && git fetch --quiet origin main && rm -rf /opt/vitalo/new-scripts && mkdir -p /opt/vitalo/new-scripts && git archive origin/main scripts/server deploy/scripts | tar -x -C /opt/vitalo/new-scripts && ls /opt/vitalo/new-scripts/scripts/server'
```

Что делает: скачивает новый код в хранилище и распаковывает **только скрипты** в папку `/opt/vitalo/new-scripts`.
Хорошо: список из шести файлов — `backup.sh healthcheck.sh preflight.sh restore-check.sh transfer-restore.sh transfer-swap.sh`.

### 0.3 Проверка сервера

```bash
sudo /opt/vitalo/new-scripts/scripts/server/preflight.sh
```

Что делает: проверяет версии программ, место на диске, брандмауэр, вход по SSH, fail2ban, службы, сертификат,
файл настроек (показывает только **имена** заполненных ключей, без значений).

Хорошо, если:

- `ХОРОШО    наружу открыты только 22, 80, 443`
- `ХОРОШО    PostgreSQL (порт 5432) доступен только с самого сервера`
- `ХОРОШО    API (порт 3000) доступен только с самого сервера`
- Redis — «не слушает» (он на сервере не нужен) или «доступен только с самого сервера»
- `ХОРОШО    вход по паролю выключен (только по ключу)`
- `ХОРОШО    fail2ban работает`
- `ХОРОШО    свободно на диске …` (не меньше 5 ГБ)
- в конце: `ИТОГ: можно продолжать`

Строки `ВНИМАНИЕ` прочитайте, они не останавливают переезд. Если есть хоть одна строка `ПЛОХО` — в ней же написано,
что сделать; исправьте и запустите проверку снова.

**Проверка фазы 0:** итог «можно продолжать».

## Фаза 2. Обновление кода и базы на сервере

### Что важно знать

На сервере сейчас стоит **старая версия** скрипта обновления: она применяет миграции сама и не понимает `--check`.
Поэтому первый запуск делаем **новым** скриптом из папки `/opt/vitalo/new-scripts` (он уже скачан в фазе 0).

Проверьте, какая версия стоит:

```bash
grep -c -- '--check' /opt/vitalo/app/deploy/scripts/update.sh
```

- `0` — старая версия: используйте команды ниже как написано (с `/opt/vitalo/new-scripts/...`).
- число больше 0 — уже новая: во всех командах ниже можно заменить `/opt/vitalo/new-scripts/deploy/scripts/update.sh`
  на `/opt/vitalo/app/deploy/scripts/update.sh`.

### 2.1 Посмотреть, что придёт (ничего не меняется)

sudo -iu vitalo /opt/vitalo/new-scripts/deploy/scripts/update.sh --check

Что делает: показывает, какой код сейчас работает, какой придёт и какие миграции базы ещё не применены.
Хорошо: строка «Режим --check: ничего не меняется» и список новых миграций.

Ожидаемый список миграций (по порядку, каждая только **добавляет** таблицы и колонки, существующие данные не меняет):

### 2.2 Обновить

```bash

```

Что делает (сам, по шагам 1/9…9/9): ещё одна копия базы → замена кода → установка зависимостей → миграции →
сборка API, магазина и админки → перезапуск служб → проверка. Занимает 5–15 минут; магазин во время сборки работает,
в конце перезапуск на несколько секунд.

Хорошо: последняя строка **«API отвечает. Готово.»**

### 2.3 Проверка

```bash
sudo /opt/vitalo/app/scripts/server/healthcheck.sh
```

Хорошо: строки `ХОРОШО  API отвечает, база данных отвечает`, все службы работают, `ИТОГ: всё в порядке`.
Откройте https://admin.vitalo.uz (через бота, команда `/admin`) — появились разделы «Заказы Яндекса», «Аналитика»,
«Финансы». Данных в них пока нет — они приедут в фазе 3.

Папка `/opt/vitalo/new-scripts` больше не нужна: `sudo -iu vitalo rm -rf /opt/vitalo/new-scripts`.
Дальше все скрипты берутся из `/opt/vitalo/app/scripts/server/`.

### Если что-то пошло не так (откат)

- **Скрипт остановился с ошибкой до шага 9/9.** Магазин, скорее всего, продолжает работать на старом коде. Пришлите
  вывод. Ничего не удаляйте.
- **API не отвечает после обновления:** `journalctl -u vitalo-api -n 50 --no-pager` — пришлите вывод (секретов там нет).
- **Вернуть базу, какой она была до обновления** (только если миграции что-то испортили — это крайняя мера):

  ```bash
  sudo -iu vitalo bash -c 'ls -1t /var/backups/vitalo/db-*.dump | head -n 3'
  sudo /opt/vitalo/app/scripts/server/transfer-restore.sh /var/backups/vitalo/db-<ДАТА-ДО-ОБНОВЛЕНИЯ>.dump
  sudo /opt/vitalo/app/scripts/server/transfer-swap.sh
  ```

  Копия восстанавливается в новую базу рядом, затем базы меняются местами; нынешняя база не удаляется, а
  переименовывается (как в фазе 3). Службы после этого остановлены — их запускают уже со старым кодом.

  После этого нужен и старый код: на компьютере `git push server 2016a61:main --force` **делать только вместе с
  разработчиком** — это единственная команда в инструкции, которая переписывает историю на сервере.

**Проверка фазы 2:** «API отвечает. Готово.», healthcheck — «всё в порядке», админка открывается.

## Фаза 3. Перенос данных с компьютера

### Почему именно так

Напечатанные этикетки должны совпасть с базой: номер на банке `V-000184` — это запись в базе с тем же номером, сроком
годности, себестоимостью и историей. Если загружать товары и банки на сервер заново, номера выдадутся другие и
этикетки придётся перепечатывать. Поэтому переносим **базу целиком**: копия `vitalo_dev` → восстановление на сервере.
Все Physical ID, остатки, SKU-алиасы, настройки и история переезжают как есть.

Способ безопасный, потому что:

- копия восстанавливается в **новую базу рядом** (`vitalo_new`), рабочая база при этом не трогается;
- вы сверяете числа и только потом одной командой меняете базы местами;
- старая серверная база **не удаляется**, а переименовывается — вернуть её можно за минуту.

### Что будет с тем, что сейчас в серверной базе

После замены в магазине будет видно только то, что было на компьютере. Всё, что есть **только на сервере** (сотрудники,
добавленные там; реквизиты карты, если вы вписывали их в серверной админке; покупатели и заказы, если они там были),
останется в старой базе и в копии, но в магазине пропадёт.

> **Остановитесь и спросите**, если на сервере уже были **настоящие** заказы покупателей. Тогда нужен другой план.
> Сколько на сервере заказов и покупателей, покажет шаг 3.4 (правая колонка «рабочая»).

### Что с тестовыми заказами и тестовыми сотрудниками

**Тестовые заказы остаются в базе с пометкой «ТЕСТ».** Удалять их нельзя: у каждого тестового заказа есть банки, а у
банок — история («зарезервирована под заказ №…», «передана в доставку», «возврат»). Если удалить заказ, история банок
будет ссылаться на заказ, которого нет, остатки и «Сверка» перестанут сходиться с движениями склада, а журнал аудита
потеряет смысл. Пометка «ТЕСТ» решает задачу без риска: такие заказы не входят в аналитику, налог и сводки, а в списке
скрываются галочкой «Скрыть тестовые».

**Тестовые покупатели** остаются (на них ссылаются тестовые заказы). Они никому не мешают: это вы сами и ваши
проверочные аккаунты.

**Демо-сотрудники** («Админ (тест)», «Менеджер (тест)», «Склад (тест)», «Маркетолог (тест)») будут **заблокированы**
скриптом на шаге 3.6. Войти под ними на сервере и так нельзя (вход «без Telegram» есть только на домашнем компьютере),
блокировка — для порядка.

### 3.1 На компьютере: подготовка базы

1. Остановите всё: `stop.bat`.
2. Убедитесь, что к `vitalo_dev` применены все миграции, включая Этап 3
   ([STAGE_3_REPORT.md](operations/STAGE_3_REPORT.md), раздел «Миграция»). Если нет — примените по отчёту,
   запустите `start.bat`, проверьте магазин и снова `stop.bat`.
3. Пометьте тестовые заказы (если ещё не помечены): отчёт Этапа 3, раздел «Как пометить старые тестовые заказы».
   **Настоящие заказы Яндекса не помечайте.**

### 3.2 На компьютере: копия базы

```powershell
cd C:\Users\PC_LENOVO\Documents\VITALO\vitalo
powershell -ExecutionPolicy Bypass -File scripts\export-dev-db.ps1
```

Что делает: проверяет, что всё остановлено и миграции применены, делает копию в `backups\vitalo_dev-for-server-<дата>.dump`,
проверяет её и печатает числа для сверки. Базу `vitalo_dev` только читает.

Хорошо: зелёная строка `Готово: backups\vitalo_dev-for-server-….dump` и таблица чисел. **Не закрывайте это окно** —
числа понадобятся на шаге 3.4.

> С этого момента и до конца фазы 3 **ничего не меняйте на компьютере**: не принимайте товар, не собирайте заказы.
> Всё, что изменится после копии, на сервер не попадёт.

### 3.3 Отправить копию и фото на сервер

```powershell
scp (Get-ChildItem backups\vitalo_dev-for-server-*.dump | Sort-Object LastWriteTime | Select-Object -Last 1).FullName vitalo@91.213.99.230:/opt/vitalo/import/
scp -r apps\api\uploads\products vitalo@91.213.99.230:/var/lib/vitalo/uploads/
```

Что делает: первая команда отправляет самую свежую копию базы, вторая — фото товаров (в базе хранятся только адреса
фото, сами файлы лежат в папке). Хорошо: обе команды дошли до 100 % без ошибок.

### 3.4 На сервере: восстановить копию РЯДОМ с рабочей базой

```bash
sudo /opt/vitalo/app/scripts/server/transfer-restore.sh "$(sudo -u vitalo bash -c 'ls -1t /opt/vitalo/import/vitalo_dev-for-server-*.dump | head -n 1')"
```

Что делает: создаёт новую базу `vitalo_new`, восстанавливает в неё копию и печатает таблицу: слева — что в новой
базе, справа — что сейчас в рабочей. Рабочая база и магазин не затрагиваются.

Хорошо:

- левая колонка **совпадает** с числами из окна PowerShell (шаг 3.2): товары, банки, банки на полке, остаток,
  альтернативные SKU, заказы;
- «последняя миграция в новой базе: `20261014100000_stage3_finance`»;
- строки «защит от ошибок (триггеров)» и «индексов» в левой колонке не нулевые (26 триггеров на момент переезда).

Во время работы скрипт пишет три шага: «структура…», «данные…», «индексы, проверки и защиты (триггеры)…».

**Если скрипт остановился с ошибкой** — рабочая база не тронута, неполную базу `vitalo_new` он удалил сам.
Пришлите текст ошибки; после исправления шаг просто запускается заново.

> Под каким пользователем идёт восстановление. Всё восстанавливается от имени `vitalo` — обычного пользователя базы,
> **не** суперпользователя (так же работает сам магазин), поэтому все таблицы сразу принадлежат ему. Владельцы и права
> из копии не переносятся (`--no-owner`, `--no-acl`), комментарии тоже (`--no-comments`). Расширения `pg_trgm` и
> `unaccent` создаются заранее самим `vitalo` — это разрешено владельцу базы.

Посмотрите правую колонку: сколько на сервере **сейчас** заказов и покупателей. Если там есть настоящие заказы —
остановитесь (см. выше).

Не совпало или передумали — удалите новую базу, ничего не пострадало: `sudo -u postgres dropdb vitalo_new`.

### 3.5 На сервере: поменять базы местами

```bash
sudo /opt/vitalo/app/scripts/server/transfer-swap.sh
```

Что делает: спрашивает подтверждение (нужно напечатать слово `REPLACE` латинскими буквами), останавливает API и бота, делает ещё одну
копию нынешней базы, переименовывает: `vitalo` → `vitalo_before_transfer_<дата>`, `vitalo_new` → `vitalo`.
Ничего не удаляет. **Службы остаются остановленными** — так и должно быть.

Хорошо: «ГОТОВО: рабочая база теперь — копия с компьютера», ниже напечатано «КАК ВЕРНУТЬ ВСЁ НАЗАД» — скопируйте эти

### 3.6 На сервере: обезвредить то, что не должно было переехать

Сначала проверка (ничего не меняет):

```bash

```

Что делает: показывает, что будет сделано, и список для сверки. Хорошо: первая строка `база vitalo`, далее:

  разослал бы их);

- какие демо-сотрудники будут заблокированы;
- список сотрудников — **убедитесь, что вы сами там есть как admin и «активен»**;

Хорошо: строка `ГОТОВО: сообщений пропущено …, входов удалено …, демо-сотрудников заблокировано …`.

## Фаза 6. Уведомления Яндекса (вебхук)

Зачем: Яндекс сам сообщает о новом заказе за секунды. Опрос раз в 5 минут **остаётся включённым как запасной** —
если уведомление потеряется, заказ всё равно придёт с опросом.

Как защищено: у Яндекса нет подписи уведомлений, поэтому (1) в адресе есть длинный секрет, (2) сервер принимает
уведомления только с адресов Яндекса: `5.45.207.0/25`, `141.8.142.0/25`, `5.255.253.0/25`. В уведомлении только номер
заказа; сам заказ сервер запрашивает у Яндекса своим токеном (только чтение).

Делайте эту фазу после 4.6 (пробный режим работает).

### 6.1 Создать секрет и включить

```bash
sudo -iu vitalo bash -c 'F=/opt/vitalo/app/apps/api/.env; S=$(openssl rand -hex 24); for kv in "YANDEX_WEBHOOK_SECRET=$S" "YANDEX_WEBHOOK_ENABLED=true" "YANDEX_WEBHOOK_CHECK_IP=true"; do k=${kv%%=*}; if grep -q "^$k=" $F; then sed -i "s|^$k=.*|$kv|" $F; else echo "$kv" >> $F; fi; done; chmod 600 $F; echo "ВЕБХУК ВКЛЮЧЁН В НАСТРОЙКАХ"'
sudo systemctl restart vitalo-api
```

Хорошо: «ВЕБХУК ВКЛЮЧЁН В НАСТРОЙКАХ».

### 6.2 Получить адрес для кабинета Яндекса

```bash
sudo -iu vitalo bash -c 'echo "https://api.vitalo.uz/api/yandex/notifications/$(grep "^YANDEX_WEBHOOK_SECRET=" /opt/vitalo/app/apps/api/.env | cut -d= -f2)"'
```

Что делает: печатает полный адрес. **Этот адрес — секрет**: скопируйте его сразу в кабинет Яндекса, не присылайте
в чат и не сохраняйте в заметках. После копирования очистите экран: `clear`.

### 6.3 Проверка с сервера (без Яндекса)

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -X POST -H 'content-type: application/json' -d '{"notificationType":"PING"}' https://api.vitalo.uz/api/yandex/notifications/nepravilnyy-sekret-0000
sudo -iu vitalo bash -c 'curl -sS -o /dev/null -w "%{http_code}\n" -X POST -H "content-type: application/json" -d "{\"notificationType\":\"PING\"}" "https://api.vitalo.uz/api/yandex/notifications/$(grep "^YANDEX_WEBHOOK_SECRET=" /opt/vitalo/app/apps/api/.env | cut -d= -f2)"'
```

Хорошо: первая команда — `404` (неверный секрет: адреса «не существует»); вторая — `403` (секрет верный, но запрос
пришёл не с адреса Яндекса — так и должно быть). Если вторая вернула `404` — вебхук не включился: проверьте шаг 6.1.

### 6.4 Зарегистрировать адрес в кабинете Яндекса

В кабинете продавца Яндекс Маркета: **Настройки → API и модули → API-уведомления** (название раздела может немного
отличаться). Вставьте адрес из шага 6.2, выберите уведомления о заказах (создание заказа, изменение статуса, отмена)

> Точное расположение этой настройки в кабинете я проверить не могу — если раздела нет или он выглядит иначе, пришлите

### 6.5 Проверка

Сделайте в Яндексе тестовый заказ (или дождитесь настоящего). В админке → **Синхронизация Яндекса** в списке

Выключить вебхук в любой момент: в `.env` `YANDEX_WEBHOOK_ENABLED=false` и `sudo systemctl restart vitalo-api`.

**Проверка фазы 6:** коды `404` и `403`, в кабинете адрес принят, появился запуск «уведомление».

## Фаза 7. Резервные копии

### 7.1 Что делается само

Каждую ночь в 03:30 служба `vitalo-backup.timer` сохраняет в `/var/backups/vitalo`:

- `db-ГГГГММДД-ЧЧММ.dump` — база (сразу проверяется, что файл читается);
- `uploads-….tar.gz` — фото товаров;
- `env-….env` — копия файла настроек (с секретами; папка закрыта для всех, кроме `vitalo`).

Хранятся 14 дней, старые удаляются сами. Ещё одна копия базы делается перед каждым обновлением.

```bash
systemctl list-timers vitalo-backup.timer
sudo -iu vitalo /opt/vitalo/app/deploy/scripts/backup.sh
sudo -iu vitalo ls -lh /var/backups/vitalo | tail -n 6
```

Хорошо: у таймера в колонке NEXT — ближайшие 03:30; вторая команда вывела «База: … проверена»; в списке свежие файлы.

### 7.2 Проверка, что из копии можно восстановиться

```bash
sudo /opt/vitalo/app/scripts/server/restore-check.sh
```

Что делает: восстанавливает самую свежую копию во **временную** базу `vitalo_restore_check`, сравнивает число строк в
главных таблицах с рабочей базой и удаляет временную. Рабочую базу только читает.

Хорошо: таблица, где колонки «в копии» и «сейчас» близки (в рабочей может быть чуть больше — она новее), и строка
**«ХОРОШО: копия восстанавливается»**. Делайте эту проверку раз в месяц и после каждого крупного обновления.

### 7.3 Забирать копии к себе

Копии на самом сервере не спасут, если сервер пропадёт целиком. Раз в неделю (и перед любым обновлением):

```powershell
scp "vitalo@91.213.99.230:/var/backups/vitalo/db-*.dump" D:\VITALO-backups\
scp "vitalo@91.213.99.230:/var/backups/vitalo/uploads-*.tar.gz" D:\VITALO-backups\
```

Хорошо: в `D:\VITALO-backups` появились свежие файлы. Старые удаляйте вручную, оставляя несколько последних.

### 7.4 Настоящее восстановление (только при потере данных)

```bash
sudo /opt/vitalo/app/scripts/server/transfer-restore.sh /var/backups/vitalo/db-<ДАТА>.dump
sudo /opt/vitalo/app/scripts/server/transfer-swap.sh
sudo systemctl start vitalo-api vitalo-bot && sleep 5 && sudo /opt/vitalo/app/scripts/server/healthcheck.sh
```

Что делает: первая команда восстанавливает копию в новую базу **рядом** с рабочей и показывает числа; вторая (после
слова `REPLACE`) останавливает магазин и меняет базы местами — нынешняя база не удаляется, а получает имя
`vitalo_before_transfer_<дата>`; третья запускает магазин и проверяет его. `server:after-transfer` здесь не нужен.
Так надёжнее, чем восстанавливать поверх рабочей базы: если копия окажется плохой, вы ничего не потеряете.

Фото: `sudo -iu vitalo tar -xzf /var/backups/vitalo/uploads-<ДАТА>.tar.gz -C /var/lib/vitalo`.

**Проверка фазы 7:** таймер включён, ручная копия сделана, `restore-check.sh` — «ХОРОШО», копия лежит на вашем компьютере.

## Фаза 8. Боевой бот

**Как бот работает.** Бот сам опрашивает Telegram (long polling), вебхука у бота в коде нет. Поэтому:

- входящий порт для бота открывать не нужно;
- **один токен — один работающий бот.** Боевой токен стоит только на сервере, тестовый — только на компьютере.
  Если запустить два бота с одним токеном, они будут мешать друг другу (ошибка 409 в журнале).

Кнопку меню «Магазин» и список команд бот ставит **сам** при запуске — адрес берёт из `MINIAPP_URL`.

### 8.1 В @BotFather (боевой бот)

1. `/mybots` → @vitalo_uz_bot → **Bot Settings → Configure Mini App → Enable Mini App**.
2. Адрес: `https://vitalo.uz`
3. По желанию: `/setdescription`, `/setabouttext`, `/setuserpic`.

Что это даёт: кнопка «Открыть» в профиле бота и ссылки вида `t.me/vitalo_uz_bot?startapp=…`.

### 8.2 Проверка

```bash
journalctl -u vitalo-bot -n 20 --no-pager
```

Хорошо: строка `[bot] @vitalo_uz_bot is running. Mini App: https://vitalo.uz`. Плохо: `409 Conflict` — этот токен
запущен где-то ещё (проверьте, что на компьютере в `.env` стоит токен **тестового** бота).

В Telegram: напишите боевому боту `/start` → кнопка «Магазин» → открывается магазин с вашим каталогом.
Команда `/admin` → кнопка в админку (есть только у сотрудников).

Туннель Cloudflare на сервере не запускается и не нужен: адреса постоянные.

**Проверка фазы 8:** бот отвечает, магазин и админка открываются из бота.

## Фаза 9. Тестовый заказ на сервере от начала до конца

Нужен товар с учётом по банкам, у которого на полке есть хотя бы 2 банки. Заказ делайте на себя.
**Сразу после оформления пометьте заказ тестовым** (карточка заказа → «Финансы заказа» → «Пометить тестовым»),
чтобы он не попал в налог и аналитику.

1. **Остаток до.** Админка → Склад → Остатки: запомните остаток и резерв товара.
2. **Оформление.** Боевой бот → «Магазин» → товар → корзина → оформление → «Перевод на карту» → «Я оплатил(а)».
   В админке: резерв +1. Вам как сотруднику пришло сообщение в бот о новом заказе.
3. **Оплата.** Админка → заказ → «Подтвердить оплату». Появился блок «Сборка: банки заказа» с конкретной банкой.
   Покупателю в бот пришло «Оплачен».
4. **Банка.** Возьмите с полки именно ту банку, что рекомендована, введите (или отсканируйте) её Physical ID → «собрана».
5. **Сборка → Передан в доставку.** Остаток уменьшился на 1, резерв 0. Банка — «В доставке (VITALO)».
6. **Возврат.** «Оформить возврат» → причина. Затем Склад → Единицы → «Возвраты на проверке» → «вернуть на склад».
   Остаток снова как в шаге 1.
7. **Отмена до отправки.** Второй заказ → «Подтвердить оплату» → «Отменить заказ». Банка сразу «На складе», резерв 0.
8. **Сверка.** Склад → Сверка: у товара «сходится».
9. **Права ролей.** Войдите менеджером и складом (или попросите сотрудников): у них **нет** пунктов «Аналитика»,
   «Финансы», «Настройки», «Журнал аудита»; склад не видит клиентов.
10. **Печать этикетки.** Склад → Единицы → выберите банку → печать этикетки 58×40. Проверьте, что QR-код читается и
    номер совпадает ([PRINT_SETUP.md](PRINT_SETUP.md)). Печать идёт с вашего компьютера через браузер.
11. **Задачи.** В заказах появились задачи менеджеру на возврат денег — закройте их (деньги за тестовые заказы никому
    не переводились).

**Проверка фазы 9:** остаток вернулся к исходному, «Сверка» сходится, оба заказа помечены «ТЕСТ».

## Фаза 10. Домашний компьютер после запуска сервера

Теперь главный — сервер. Компьютер остаётся для разработки и не должен вмешиваться в работу магазина.

1. **Выключить опрос Яндекса на компьютере.** В `apps\api\.env`:

   ```
   YANDEX_SYNC_ENABLED=false
   YANDEX_SYNC_DRY_RUN=true
   ```

   Зачем: иначе два экземпляра будут опрашивать Яндекс одновременно, и каждый создаст заказы и зарезервирует банки в
   своей базе.
2. **Токен Яндекса.** Старый токен, который стоял на компьютере, **отзовите** в кабинете Яндекса (на сервере стоит
   новый). На компьютере `YANDEX_API_KEY` можно оставить пустым.
3. **Бот.** На компьютере в `.env` должен быть токен **тестового** бота. Боевой токен на компьютер не вписывайте.
   Тогда ничего с компьютера в боевой бот уйти не может.
4. **База `vitalo_dev`** на компьютере теперь — учебная. Приёмку, сборку и заказы ведите **только в серверной админке**
   https://admin.vitalo.uz. Не принимайте товар в локальной базе: Physical ID на сервере и на компьютере разойдутся.
5. `start.bat` и туннель работают как раньше — для проверки новых версий.

После шага 1 можно включить рабочий режим Яндекса на сервере (шаг 4.7).

**Проверка фазы 10:** в локальной админке → Синхронизация Яндекса: «Опрос: выключен».

## Фаза 11. Чек-лист перед открытием

**Секреты**

- [ ] `TELEGRAM_BOT_TOKEN` на сервере — боевого бота; на компьютере — тестового.
- [ ] `BOT_API_SECRET` на сервере — новый (шаг 4.3).
- [ ] `YANDEX_API_KEY` на сервере — новый, только чтение; старый отозван.
- [ ] `YANDEX_WEBHOOK_SECRET` создан на сервере и нигде не записан, кроме `.env` и кабинета Яндекса.
- [ ] Файл `.env`: права `600 vitalo`. Секреты не отправлялись в чат и не попадали на скриншоты.

**Настройки магазина** (админка → Настройки)

- [ ] «Перевод на карту» и «Перевод по реквизитам»: **настоящие** номер карты, получатель, реквизиты (без пометки ТЕСТ).
- [ ] Доставка: цены и сроки по регионам проверены, отметка «тестовый» снята, порог бесплатной доставки верный.
- [ ] Документы: опубликованы оферта и политика, проверенные юристом (не версия `0.1-test`).
- [ ] «Поддержка и время работы»: контакт и часы проверки платежей.
- [ ] Главная: баннер, плитки, «Как заказать».
- [ ] Финансы: внесены сотрудники (зарплаты), ставка налога верная.

**Данные**

- [ ] Все тестовые заказы помечены «ТЕСТ» (в списке заказов без галочки «Скрыть тестовые» нет непомеченных тестовых).
- [ ] Склад → Сверка сходится; несколько банок с полки найдены по Physical ID.
- [ ] Демо-сотрудники заблокированы; у настоящих сотрудников верные роли.
- [ ] `npm run server:after-transfer` (проверка) — в разделе «ЧТО ПРОВЕРИТЬ ДО ОТКРЫТИЯ» пусто.

**Надёжность**

- [ ] Ночной бэкап включён; `restore-check.sh` — «ХОРОШО»; свежая копия лежит на вашем компьютере.
- [ ] `preflight.sh` — «можно продолжать»; `healthcheck.sh` — «всё в порядке».
- [ ] Сертификат действует, пробное продление успешно.
- [ ] Мониторинг настроен (ниже).
- [ ] Яндекс: опрос на сервере включён, на компьютере выключен; режим переведён в рабочий (шаг 4.7).

### Мониторинг (бесплатно, 5 минут)

1. Зарегистрируйтесь на https://uptimerobot.com (или в похожем сервисе).
2. **Add New Monitor** → тип **HTTP(s)** → адрес **`https://api.vitalo.uz/api/health`** → интервал 5 минут.
3. Оповещения — на вашу почту (и в Telegram, если сервис это умеет).

Адрес открыт для всех и не содержит секретов: только «жив / не жив». Ответ `200` — всё хорошо. Ответ `503` — база не
отвечает **или** опрос Яндекса включён, но успешной синхронизации не было дольше 20 минут. Нет ответа — сервер или
API недоступны.

На самом сервере то же самое (плюс место на диске, службы, возраст копии) показывает:

```bash
sudo /opt/vitalo/app/scripts/server/healthcheck.sh
```

## Чего на сервере не делать

- Не запускать `npm run seed`, тесты и скрипты `dev:*` (они и сами откажутся при `NODE_ENV=production`).
- Не запускать туннель Cloudflare.
- Не показывать и не пересылать `.env`.
- Не открывать в брандмауэре порты 3000 и 5432.
- Не удалять базу `vitalo_before_transfer_…` раньше чем через две недели после открытия.
